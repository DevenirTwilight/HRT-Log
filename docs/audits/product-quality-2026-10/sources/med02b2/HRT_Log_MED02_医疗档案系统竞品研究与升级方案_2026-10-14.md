## 1. 核心产品决定

**产品定义改为：离线优先、以用户为中心的纵向 HRT 与医疗档案（Personal Health Record, PHR）；不是单纯加密文件夹，也不是医院 EHR 的复制品。**

三条价值链必须闭环：

1. **存得住**：PDF/图片原件、结构化记录、关联、版本/回收与密钥一起安全保存，损坏有可见状态，完整备份并能换设备恢复。
2. **找得到、看得懂**：按时间、文件类型、机构、就诊、化验、治疗时期检索；原件与手工结构化化验相互关联、来源可追溯、矛盾不被静默覆盖。
3. **用得上**：一次就诊前快速准备要讨论的问题、化验趋势、已确认的实际用药事实及用户选定原件；分享遵从显式选择和最小披露。

**保留的不可协商边界**：不增加 INTERNET、云账号、远程分析 SDK；PRIMARY/伪装空间的加密身份与数据严格隔离；不提供自动诊断/剂量调整；不修改历史真实用药流水；不把研究性 M2 估算当成个人实验室实测值；完整可信备份前不能开放“唯一原件”的正式医疗附件库。

## 3. 与原 MED-02 计划的变更清单（保留/修改/增加/延期/删除）

### 3.1 保留

- SQLCipher 加密元数据 + 私有目录独立不可变密文对象；不向旧 `PNBAK1` 塞大 BLOB/base64。
- localDataset、logicalVault、physicalGeneration、recordEpoch、sessionEpoch 分离；typed stable UUID/tombstone；不能根据同日期、同文件名或重用整数 ID 自行关联。
- 每版本独立密钥、安全包裹、完整认证、关闭授权与同步事务的线性化门、显式 operation journal、数据库 CAS 最终发布。
- 严格无完整磁盘明文后备、图片解码限额、PDF ProxyFD/PdfRenderer 可行性经验；测试合成样本、真实 API 与 ARM 区分。
- 新完整医疗加密备份和跨设备恢复必须先于可用附件功能；旧 PNBAK 继续仅结构化记录，明确说明不含附件。
- 显式关联、不可变原件、多版本、回收站、纠错恢复，文件本体绝不因编辑标题/标签而被静默改写。

### 3.2 修改

1. **从“附件列表”改成“医疗资料库”**：增加待整理、最近添加、所有文件、按类别、按医疗时间线、回收站等用户入口。导航无需新增一排顶层页面；可在现有医疗档案页内子页面完成。
2. **PDF 优先级上调**：图片加密预览阶段仍可独立验收，但正式称“医疗文件管理 V1”的版本建议要求 PDF（包括多页）可以加密保存并在应用内安全查看。技术难点不允许用明文 cacheDir 降级绕过。
3. **容量不是固定产品承诺**：16 MiB/件、256 MiB/空间、1000 版本为 B0 尚未批准的候选。先收集合成真实文件体积档位与低端 ARM 资源证据；可将 16 MiB 设计成早期验证档，而不是不经测试地冻结。任何提升上限都必须重新审查 AEAD 块数/GHASH、备份总帧数、恢复双份存储、解码资源与 UI 性能，不是只改一个常量。
4. **不以内容哈希决定医疗语义**：相同原件可提示重复，但不能自动认为是同一次就诊/同份采样；默认不做跨空间去重，早期可不做物理去重，优先实现确定性身份、可靠恢复和用户纠错。
5. **OCR 不是初版门槛**：待本地多语质量、资源、模型授权、脱敏及确认流程验证后引入；任何抽取结果必须是待确认候选，不得覆盖原件或事实数据。
6. **导出共享独立于文件库**：初版明确的 SAF 用户导出/就诊资料包，不建立长期网络分享权限；外部文件副本无法由 HRT Log 撤回，必须在界面讲清。
7. **FHIR 先按语义参考设计，而不按 FHIR 逐表重构内部 DB**：可预留字段映射与后续互通 adapter，不因“国际标准”制造 20 个新业务表。

### 3.3 新增

- 分类前的**待整理收件箱（Inbox）**、批量归档、无关联/待确认标记、可见的导入进度/失败重试、原 SAF 提供者及来源可信度说明。
- 用户最常用的**筛选和搜索**：标题、类别、用户标签、机构、报告日期、文件导入日期、关联就诊、关联 Lab；默认数据均存密文数据库内；初版只搜索已录入元数据，不宣传 PDF 全文搜索。
- 文档双日期+来源元数据：**采样/就诊等临床事件日期、文件签发日期、用户导入日期**分别存放；未知可留空；时区/日期精度可表达只有年月或仅日期；对外显示默认临床日期，不能与签发/导入混同。
- **原始文件 ↔ 结构化数据双向跳转**：从 Lab 打开证据原件；从原件查看明确关联的化验值和就诊，不擅自拉取“当天所有”记录。
- **文件状态与异常可见性**：未分类、未关联、已归档、在回收站、原件缺失、认证失败、旧身份已隔离；不能把损坏文件渲染为空白且显示正常。
- **选择性医生资料包（Visit Packet）**：明确时间段、用药、化验、就诊备注、用户选定附件；导出前预览清单并提示未包含的项目；保留来源与时间，不把研究模型值伪装为测量结果。
- **多文件同一次就诊或检查**：一次就诊可关联处方、检查报告、诊后说明多个文件；一份报告可包含多个化验项，多个报告可属于一次就诊；从归档到归属始终由用户确认。
- **安全的原件版本+注释**：标题/注释/标记/用户备注是可更正元数据；高亮或页码注释初期作为加密附属记录，不直接修改原始 PDF 字节。旧报告被更正时保留替代关系与来源。
- **隐私最小披露检查表**：面向医生/其他用途的包，区分默认不分享、用户本次选取、提供原件还是摘要；如需视觉遮盖必须采用真正移除底层内容的另生成副本，而非在 PDF 叠黑框。
- **导入与恢复健康度**：统计已完整备份/未备份的文件数量与最新备份完成时间（不向伪装空间展示）；可进行受控完整性检查；不能把备份时间等同实际外部云端永久保存。

### 3.4 延后 / 排除

- 延后：文档原文全文索引、多语言离线 OCR、自动结构化 Lab 解析、DICOM 大影像、电子签章验证、HL7 FHIR/CDA 导入导出、医生/机构去重自动合并、跨设备自动同步、复杂 redaction。
- 明确排除本阶段：云账户、医院门户账号自动抓取、网络医疗消息、多人共同编辑、家庭代理账户、AI 诊断/处方或剂量决策；不引入联网 SDK/遥测。
- 可由用户以后再考虑：Scan 功能通过系统相机/外部扫描应用的导入路径。外部扫描应用可能产生明文副本或云端上传；不能把这样的流程默称“端到端私密”。优先支持用户已有 PDF/图片的 SAF 导入。

## 4. 建议的信息架构与交互流程

### 4.1 医疗档案主页（复用现有入口）

```
医疗档案
[搜索医疗资料…]
[添加文件]   [为就诊准备资料]

待整理（N）   最近资料   全部资料
按类别：化验报告 / 处方 / 就诊说明 / 医疗证明 / 影像报告 / 其他
按时间：临床时间线（关联既有 HRT 治疗时期）

就诊记录 / 化验记录 / 医生机构（既有或未来）
更多：未关联文件 / 回收站 / 备份与恢复说明
```

如无附件功能上线，隐藏不可点击的文件入口，现有 MED01 就诊能力正常使用；不要用空壳入口提前宣布支持。

### 4.2 导入新文件（四步，允许稍后整理）

1. 用户从系统 SAF 选文件；应用内显示 MIME 检查、大小、当前安全能力和预计影响。无权访问原 SAF provider 时清楚解释。
2. 流式认证加密导入，必须真实 EOF / 元数据提交成功才标完成；可取消，失败不会产生假文件或失去旧版本。
3. 简易分类：文件标题、类别、临床日期、出具机构（可选），可选“稍后整理”；不强迫用户在导入时先创造不存在的就诊/化验 ID。
4. 关联：可选现有就诊、化验或时期；明确 user-confirmed、支持多选和日后改正；不能因同一天发生自动建立强语义关联。

**用户感受目标**：导入可成功后再整理；归档补录有批量操作；核心找文件流程不需要进入数据库式的技术表单。

### 4.3 单文件详情

```
[安全预览（PDF 或图片）]
2026-09-21 · 化验报告
出具机构（用户录入，未核验）

原件：PDF / 页数 / 大小 / 原始哈希校验状态
日期：采样日期 / 出具日期 / 导入日期
关联：就诊A、Lab记录3项
备注和标签、可见的来源类型

[查看化验结果] [用于本次就诊]
[修改信息] [替换原件] [移至回收站]
```

初版不必常显 UUID、加密算法、操作日志。高级诊断页可提供有限可验证信息，但不得向普通 UI 或日志输出敏感标题/原文件名。

### 4.4 就诊资料包（用户主动组装）

1. 选择既有 Appointment 或临时新建“此次要分享的资料包”；范围默认与该次就诊相关，不默认全库。
2. 自主勾选：就诊问题、选定时期规则、实际服药统计、化验及参考区间（可用时）、选定 PDF/图片、药物清单。
3. 明确每条来源：“用户手动输入/已保存原件/应用内部实际记录”；模型估算单独标注或默认不选入。
4. 导出前提供目录预览、总页数/总文件大小和敏感文件列表，用户最后明确确认；必要时可“只打印/导出摘要”或“摘要+原件”。
5. 只向用户明确选择的 SAF 目的地写入明文导出；写出后应用不能删除对方保存的副本。若扩展 ACTION_SEND / 一次性 content URI，需要另验授权生命周期和外部应用缓存，不能把权限到期说成副本撤销。

## 5. FHIR 启发的数据语义：少改结构、多留互通余地

HL7 FHIR `DocumentReference` 用于文档发现及元数据（内容 MIME、作者、出具时间、状态、上下文/就诊和文件版本关系），并非一定要求在数据库中把整个文件存成 FHIR JSON。`DiagnosticReport` 可以组织多条 `Observation`、`Specimen` 与原报告 `presentedForm`。建议采用以下逻辑概念，不立即承诺新的 Room 表：

| 概念 | 作用与 HRT 旧实体关系 | 强制约束 |
|---|---|---|
| MedicalDocument（既定 document identity） | 患者管理的某份资料，包含标题/类别/临床日期/机构/标签 | 不因文件重新扫描创建自动临床事实 |
| DocumentVersion（既定 immutable version） | 原始内容和替换版本、encrypted object handle | 原件不可变，替换生成新版本/新密钥 |
| DocumentLink（既定 typed link） | 指向现有 Appointment、LabValue、历史 Dose 等 | 只由用户明确确认；稳定 identity 防同整数ID错配 |
| DocumentSource / Provenance（新增逻辑字段） | 源机构的用户陈述、文件导入方式、手动提取状态 | 不要将自报“医院原件”表述为系统核验的签发真实性 |
| LabReport（中期新逻辑概念） | 组织一份报告与多条现有 LabValue | 一份报告不必等于一份标本；不能按日期自动强并 |
| SampleGroup（中期可选） | 同次采样/标本/时间/机构信息 | 仅有可靠证据或用户确认时建立，不能改写 LabContext 冻结快照 |
| ShareManifest（可先临时生成） | 一次性就诊导出所选事实与附件及版本 | 精确列明所选内容，不能无意共享全库；默认不持久存明文 |

在 #29 Room10 基础完成且合并前不要把此逻辑模型直接塞进 #29 的已批准八表，也不改原 29 张既有表；字段扩展、新索引、医疗报告/采样实体应单独 ADR 与 additive migration 审查。

## 6. 安全与隐私的新增产品规则

- **隐私标签 ≠ 密码权限**：例如“普通/敏感/仅个人”用于筛选与分享默认值，不能对外宣称实现了远程医生用户级 ACL；应用实际只有本地 PRIMARY 解锁/伪装隔离及明确导出的信任边界。
- **来源可核查**：字段 `sourceType` 可表示 USER_UPLOADED / USER_TRANSCRIBED / PROVIDED_BY_CLINIC_CLAIMED 等；外部签章校验需单独实现，不能依靠文件名/Logo/哈希推断真伪。
- **原件与提取数据分开**：OCR/人工输入可错；保留原件和修订轨迹，LabValue 的修订有独立语义，不得直接改字节、污染已冻结历史或让异常值变成伪造正常。
- **导出前检查**：显示明确选取清单和可见的敏感数据提醒；只开放真实有权限且经测试的导出方式。
- **锁定与撤权**：viewer、thumbnail、reader、DB transaction commit、备份导出和内容解析均受 session/epoch 与具体 scope 约束；“锁定后以后不要再启动新读取”不足以保护已经打开的 FD。
- **备份一致性**：所有仍有效的附件版本、回收站/历史、引用和可移植密钥必须在同一个完整包经过认证；如果只备份记录，在 UI 显示“不含医疗文件原件”。已恢复但缺少对象时展示损坏/缺失，不凭空重建文件。
- **消除意外泄露**：系统最近任务、截图/投屏、Notification、存储选择器、FileProvider、键盘/剪贴板、日志、缓存、导出目的地、Android OS 自动备份范围各有专项验收。Android Storage Access Framework 可以避免广泛存储权限，但不代表 SAF 来源永远是本地或安全。
- **安全审查**：正式 AEAD 组合、流式备份/KDF、密钥包裹、恢复与 host parsers 要独立复核；对照 OWASP MASVS。合成 POC、AI peer review、JVM/API 模拟器测试不等于正式安全认证。
- **容量与保留**：回收站及历史版本初期不自动到期删除；硬上限由加密预算+ARM测量确定。完整恢复必须先保留旧资料与新 staging，不能在空间不足时先删除旧资料。

## 7. 重排开发路线：先完成安全底座，再交付真实用户价值

下列是**新版提案**，不覆盖原 PR #27/#28/#29 授权与状态。每批应有 ADR / 源码基线 / 失败测试 / 四语 UI / 真实设备缺口 / 最终 HEAD CI 报告。任何生产 Schema / 加密协议 / 完整备份 / 正式功能启用，仍逐项取得用户批准。

| 阶段 | 建议范围 | 前置条件 | 出口验收 |
|---|---|---|---|

**B4/B5 关系**：原计划可先阶段性开放安全图片能力；升级后的**“医疗文件库 V1 完整产品门槛”**建议同时有 PDF 预览。若后来单独开放图片 Beta，应明确标成“图片附件 Beta”，不能宣称已覆盖完整医疗文件管理。

**C1/C2 可并行进行交互原型与免迁移快捷录入研究**，但不能在 B1 schema 尚未稳定时进行与其冲突的同分支数据库修改。C2 中涉及附件实体打包，生产功能要等 B3/B5 才能完成。

## 8. 核心验收场景（示例）

| 场景 | 必须证明 |
|---|---|
| 两张图片同一次检查 | 可归同一检查，不因文件数创建两次检查 |
| 一个 PDF 对应 E2、T 和其他化验项目 | 一份原件明确链接多个已有 LabValue；单项更正不覆盖原件 |
| 同一日两家机构检查 | 不自动合并；日期/机构/采样身份均保留 |
| 重复导入相同 PDF | 告知可能重复，可选择保留独立资料；不静默错关联 |
| 旧文件被医院修正 | 创建新版本，旧版本保留与替换关系，旧引用可审计 |
| 导入时断电、取消、MIME 欺骗、空间不足 | 不显示半文件；旧 active 对象与现有医疗库完整保留 |
| 删除就诊、恢复和相同 integer ID 再利用 | 旧附件不自动跳到新就诊；typed stable identity 验证 |
| 伪装笔记/屏幕锁定/系统最近任务 | 不泄露 PRIMARY 的文件名、缩略图、计数、密钥与内容 |
| 换新手机还原完整备份 | 每条引用、活跃/历史/回收站文件及密码材料完整且可读；损坏包旧库不变 |
| 仅分享 3 份材料 | 导出中只能包含所选三份及本次明确勾选的摘要；不能夹带全局 Health 数据或 metadata |
| 320dp / 2×字体 / 法语/中繁英语 | 按钮可达，长文件名、日期与筛选不卡死，TalkBack 信息正确 |
| 1000份元数据与数百个PDF | UI分页/scroll稳定、内存和加密读写有界；真实ARM profile 不用模拟器外推 |

## 9. 尚需负责人作出的产品决策（不要求本研究立刻批准）

1. 医疗资料库 V1 是否必须在同一正式版本同时支持 PDF+图片预览？建议**是**，图片可提前小范围 Beta 但不可替代正式完整版。
2. 容量上限：原候选 16 MiB/256 MiB/1000是否足以满足真实 PDF 资料集？建议先采样/测试，再冻结安全硬上限与双份恢复预算，不现在武断选 64/512 MiB。
3. 文件隐私/可见性标签和分享前目录复查是否为正式 V1 功能？建议**是**；但不虚称离线“外部 ACL”。
4. 选择性导出范围：先原件+单页清单，还是同步支持结构化就诊 PDF？建议先简单安全输出、随后 C2 一次就诊包。
5. DocSource 标签允许用户陈述医院/机构，但不将其称为官方核验。是否接受？建议**接受**。
6. OCR 暂缓，优先原件、全文元数据与手工 Lab 联动；待本地性能与确认流成熟再讨论。
7. B2 密码学组合、B3 新备份协议、B6 正式启用及签名交付均需**单独审批**，本方案不授权直接执行。

## 10. 实施前建议的下一步

**最优先的工作不是立刻加表或者上 OCR，而是一个不动正式代码的 `MED-PRODUCT-V2` 设计与兼容性 PR。**

产出以下四类材料：

- 最新 PR 状态矩阵：default vs #27/#28/#29，是否全绿、当前合并依赖、正式生产代码是否包含新 schema。
- 交互需求：3个常见任务（存报告、查历史化验、为医生选资料）、导入/详情/搜索/纠错/导出的四语信息架构和可访问性样例。
- 数据/安全 ADR：上述新字段可否用 B1 现有八表实现；需要新增时具体 diff 和迁移风险；对 B2/B3 协议预算的影响。
- 分阶段开发任务/验收清单：明确一项功能可能从什么时候才可正式启用、哪些是真实 ARM 未测试、哪些属于独立安全审查阻断项。

这一步完成后可合理确定 B2/B3 工作的产品约束，而不是在做完最艰难的密码学工程后才发现文件库无法满足基本就诊流程。
