# HRT Log 欧盟适配评估：全部修改意见

- **评估对象**：[DevenirTwilight/HRT-Log](https://github.com/DevenirTwilight/HRT-Log)（Build 25 / 0.2.0，数据库 schema 9，Kotlin + Compose，离线 Android 应用）
- **评估日期**：2026-10-14
- **适用定位**：个人主导、非商业、免费开源（MIT）的隐私工具；目标用户含法国用户（参照 HAS 2025 年 7 月建议）
- **总体结论**：现有定位下欧盟适配度很高；缺口集中在**三份文档**、**一轮系统无障碍审查**、以及**商业化触发线的书面界定**。均为工作量可控的修改。

## 一、高优先级修改意见

### 1.1 添加公开隐私声明（PRIVACY.md + 应用内四语入口）

- **问题**：应用架构上"零网络、零遥测、全本地"，但仓库和应用内没有一份成型的隐私声明。GDPR 义务因"数据不离开设备"而近乎为零，但用户信任、将来任何商店上架（Play 要求 data safety 表和隐私政策 URL）、以及把隐私优势变成产品卖点，都需要这份文档。
- **证据**：README 与 `docs/REQUIREMENTS.md` 第 1 节声明无账号/无 INTERNET/无分析 SDK；CI 有权限检查；`docs/disguise-privacy.md` 记录了伪装模式的数据边界——素材齐全，只差汇总成文。
- **修改内容**：
  1. 新建仓库根目录 `PRIVACY.md`：数据全部本地存储；不申请 INTERNET 权限；无账号、无分析、无遥测、无广告；备份用 AES-256-GCM 加密且密码不出设备；CSV/PDF 导出为用户主动行为；伪装模式与私人便签的数据边界。
  2. 应用内"关于"页加入"隐私"入口（四语，进 `strings.xml` 并保持 `TranslationsTest` 通过），内容与应用实际行为逐条对应，不写任何做不到的承诺。
  3. 发布说明与 README 链接到 PRIVACY.md。
- **验收**：声明中每一条都能对应到代码或 CI 检查；四语齐全；`TranslationsTest` 通过。

### 1.2 统一的"预期用途"声明（非医疗器械定位）

- **问题**：MDR 定性看"预期用途"（intended purpose）。各功能有零散免责声明（浓度估算首进提示、D-1 决议、能力矩阵），但 README 和关于页没有一句汇总声明。一旦表述漂移（例如宣传语出现"帮你调整剂量"），就可能被认定为医疗器械软件（Class IIa，需 CE、公告机构、ISO 13485）。
- **依据**：MDR 2017/745 第 2 条 + Rule 11；[MDCG 2019-11 rev.1（2025-06）](https://health.ec.europa.eu/latest-updates/update-mdcg-2019-11-rev1-qualification-and-classification-software-regulation-eu-2017745-and-2025-06-17_en)：仅为记录/提醒、不输出诊疗决策的软件一般不构成医疗器械。
- **修改内容**：
  1. README 顶部与关于页加入固定声明（四语）：**"HRT Log 是个人记录与提醒工具，不是医疗器械，不提供医疗建议；浓度曲线是基于群体参数的估算，不能替代抽血化验；任何用药调整请咨询医生。"**
  2. 把这句话同步进发布说明模板，避免下次发布时遗漏。
  3. 在 `docs/REQUIREMENTS.md` 增加一条硬性规则：营销/宣传文字不得使用"帮你决定剂量""监测疗效""安全用药"等医疗性措辞。
- **验收**：声明四语齐全；`TranslationsTest` 通过；README 与发布说明一致。

### 1.3 书面界定商业化触发线（GPSR / CRA）

- **问题**：目前非商业，故 GPSR（适用于软件，免费与否不影响，但以"商业活动"为前提）与 CRA（开源非商业明确豁免）均不适用。但**捐赠换功能、赞助、付费解锁、代分发**等任何行为都可能被认定为商业活动，使义务立即启动：GPSR 要求欧盟境内责任人（Art. 16）与安全文档；CRA 自 2026-09-11 起已有报告义务、2027-12-11 全面适用。
- **依据**：[GPSR 2023/988 概述](https://www.mhc.ie/latest/insights/application-of-the-general-product-safety-regulation-to-software)；[CRA 时间线（EC 官方页面）](https://digital-strategy.ec.europa.eu/en/policies/cyber-resilience-act)。
- **修改内容**：
  1. 在 `docs/` 新增一页（如 `docs/eu-compliance-notes.md`）写明：**什么算商业化触发**（示例：与应用获取相关的付费、功能付费、商业分发、以推广为条件的赞助）、触发后需要做什么（GPSR 责任人/文档；CRA 漏洞与事件处理流程）、以及"纯捐赠不与产品挂钩则不构成触发"的边界。
  2. 在 CONTRIBUTING.md 中提醒：贡献不改变非商业定位。
- **验收**：一页纸即可；关键是将边界写下来，避免将来无意识跨线。

## 二、中优先级修改意见

### 2.1 系统性无障碍审查（EN 301 549 对照）

- **现状**：R-13 做了日历 TalkBack 语义（四语）、320dp/2 倍字号测试、用户真机验收过 TalkBack——方向正确但是局部修复。欧洲无障碍法案（EAA，2019/882）自 2025-06-28 适用，健康类应用是无障碍最该覆盖的场景。
- **修改内容**：
  1. 按 EN 301 549 条目做一轮全应用审查：焦点顺序、可点区域语义标签、颜色对比度（现有三档对比度设置是好基础）、动态字号不截断、TalkBack 全流程（提醒、导入/导出、备份恢复、伪装模式）。
  2. 把发现的问题记入 `docs/BACKLOG.md` 的可访问性条目，分批修复并补 Android 测试断言。
  3. 无障碍审查结论写一页验证文档（沿用现有 `*-verification.md` 的格式）。
- **验收**：全流程 TalkBack 走查通过；审查表落入仓库留档。

### 2.2 评估 F-Droid 上架（欧洲社区分发渠道）

- **理由**：纯 Java Argon2（BouncyCastle）当初就是"方便 F-Droid 构建"的技术决策；F-Droid 是欧洲（德国）社区托管的应用商店，其反遥测、反跟踪文化与本应用完全一致，且能覆盖全欧盟 Android 用户，无需 Google Play。
- **修改内容**：
  1. 准备 F-Droid 元数据（fastlane 或 F-Droid metadata 文件，含四语描述与截图）。
  2. 核对构建可复现性（F-Droid 要求能独立构建；现有 Gradle 固定版本与 wrapper 校验是加分项）。
  3. 注意：上架的是**当前独立重写引擎**的版本；Git 历史问题不阻塞 F-Droid（它从当前源码构建）。
- **验收**：F-Droid 可复现构建通过；提交收录申请。

### 2.3 Git 历史中移植代码的处置决定（书面化）

- **现状**：当前发布（0.2.0 build 4）已是文献独立重写引擎，干净；但 Git 历史与旧标签仍含无授权上游（LaoZhong-Mihari）移植代码。`docs/licensing.md` 已如实记录"不改写 Git 历史"的现状，这是对的——版权风险在欧盟语境下因"不提供下载即无分发"而很低。
- **修改内容**：只需要**做出并记录一个明确决定**：
  - 方案 A（默认推荐）：保留历史，`docs/licensing.md` 已有的披露视为最终处置；风险极低。
  - 方案 B：若追求绝对清洁，重建仓库历史（会改所有 commit SHA，需协调分支与既有 fork）。
  - 两个方案都应在文档里标注"已决定，不再悬置"。
- **验收**：`docs/licensing.md` 相应章节由"待决定"改为明确结论。

### 2.4 落实"待核实"的地区内容

- **现状**：需求文档中多处标注"待核实"：大陆个人不良反应上报官方渠道、若干雌二醇产品与螺内酯的法国说明书原文、补佳乐与国产 CPA 大陆说明书、大陆《药品网络销售禁止清单（第一版）》原文。
- **修改内容**：按 15a 第 4 条的来源优先级（企业官网/药监局 → 双站一致的第三方转载）逐条核实并更新 `docs/wellbeing-research.md`；查不到的保留"未核实"标注，不得进入界面（现有硬性规则已保证这一点，执行即可）。
- **验收**：待核实清单清零或明确标注"无法核实，不用于界面"。

## 三、远期修改意见

### 3.1 扩展更多欧盟语言

- **现状**：EN/zh-CN/zh-TW/FR 四语（`TranslationsTest` 强制四语齐全），法语对法国目标用户已足够；德国、西班牙、意大利等欧盟国家有可观的跨性别群体。
- **修改内容**：按用户增长数据决定加入德语（de-DE）或西语（es-ES）等；沿用现有"新增文字必须全语种齐全"的机制；地区相关内容（监管警示、上报渠道）随语言扩展补充对应国家条目。
- **提示**：语言扩展的同时要同步扩展地区设置内容，否则新语言用户只得到半套本地化。

### 3.2 预留与法国医疗生态互通的要求（仅备忘，不建议现在做）

- **现状**：纯离线应用，不涉及任何健康数据托管，因此**不适用**法国 HDS 托管认证与 SIS 互操作参照。若未来想接入 Mon espace santé / DMP（分享数据给医生），会立即进入 HDS 认证与 SIS 互操作强制要求的范围，成本会高一个数量级。
- **修改内容**：仅在 `docs/eu-compliance-notes.md` 中记一行备忘，防止将来无意间规划"云端同步"类功能而不评估合规成本。

### 3.3 任何"剂量决策支持"功能之前的 MDR 评估闸门

- **现状**：现有一系列硬性规则（不给剂量建议、不评判、不解读）正是维持非医疗器械地位的关键。任何新功能若输出"建议你……"式内容（剂量决策支持、疗效判断、异常值预警），按 MDCG 2019-11 rev.1 大概率构成医疗器械软件（Rule 11，Class IIa），需要 CE 标志、公告机构介入、ISO 13485 质量体系、EUDAMED 注册、欧盟境内 PRRC。
- **修改内容**：在 `docs/REQUIREMENTS.md` 硬性规则区加一条：**"任何输出诊疗决策建议的功能（剂量建议、疗效判断、异常预警）必须在动工前单独评估 MDR 医疗器械定性，未经评估不得实现。"** 一句话的闸门，成本为零。

## 四、已达标、建议保持现状的方面（无需修改）

以下不构成修改意见，但为完整性记录——这些是你已经做对的，将来 review 时别误改：

1. **GDPR 数据最小化架构**：无 INTERNET 权限、无账号、无遥测，数据不离开设备；开发者对用户健康数据不构成数据控制者。保持离线原则就是最大的合规。
2. **Art. 32 级别的安全措施**：SQLCipher、Argon2id（19 MiB、2 迭代）、Keystore、AES-256-GCM 备份、`allowBackup=false`、FLAG_SECURE、明文临时文件清理（B2）。
3. **仓库卫生**：真实健康数据永不入库（硬性规则 1）、合成测试数据、私人密钥与交付 APK 全部出库管理。
4. **MDR 边界自律**：不给剂量建议、漏服不建议补服、化验不变色不解读、不采用计分量表、估算标注群体性质、D-1 取消醒目个人浓度。
5. **地区内容设计**：监管内容按地区条件显示并注明"某国的规定"、不因 HAS 把 CPA 列为二线而贬低、不评判自行用药来源。
6. **伪装模式与脆弱用户保护**：中性包名、通知中性文案、诱饵空间、隐私边界如实记录（包括"系统设置仍显示真名"这类诚实局限）。
7. **AI 披露**："人主导、AI 实现"如实声明；应用内无 AI 功能，EU AI Act 目前不适用（PK 引擎是确定性数学，不是 AI 系统）。
8. **许可诚实**：上游无授权如实披露、未授权量表不复制、Featherline 仅用公开数值且独立推导。

## 五、建议的声明草稿（可直接采用后修改）

### PRIVACY.md / 应用内隐私声明要点（每条须有代码对应）

> HRT Log 将你的全部数据存储在本机：用药记录、库存、身心状态、化验和估算。它不申请网络权限，因此**在技术上无法发送任何数据**：没有账号、没有遥测、没有分析、没有广告。加密备份由你设置密码，用 AES-256-GCM 加密，密码不出设备。CSV/PDF 导出是你的主动操作。伪装模式与私人便签的数据边界见应用内说明。卸载会删除本地数据，请先备份。

### 预期用途声明（README / 关于页 / 发布说明通用）

> HRT Log 是个人记录与提醒工具，**不是医疗器械，不提供医疗建议**。浓度曲线基于已发表文献的群体参数估算，个体差异大，**不能替代抽血化验**。症状信息仅原样显示官方来源文字，不做判断。漏服只作记录，不建议补服或加倍。任何剂量调整、停药或换药决定，请咨询你的医生。
