## Room 9 → 10 additive migration draft (design-only)

This AI review and stdlib SQLite fixture are not an Android Room/SQLCipher migration acceptance or an external professional security certification. No production Entity, NotesDatabase, migrations, PNBAK1 or actual user database changed. `tools/attachment-design-validation/room10_draft.sql` is intentionally outside Gradle/application source sets. The synthetic runner sets only its own in-memory `user_version` to 10. Room9 checked-in JSON stays byte-for-byte unchanged.

### Actual existing behavior and consequences

`NotesRepository.deleteAppointment` snapshots appointment, visit_question and visit_pack to `Trash.APPOINTMENT`, then physically deletes the original rows. `Trash.reinsert` restores parents first with **their original integer IDs**, using CONFLICT_ABORT; `restoreTrash` removes the matching trash item only after the enclosing transaction succeeds. Labs use the same snapshot family; dose records retain soft-deleted rows and supply references. Backups validate domain table allowlists and frozen rows. Therefore a direct attachment FK to `appointment(id)` or `lab_value(id)` is unacceptable: CASCADE loses recovery links; RESTRICT breaks current deletion. A nullable foreign-key workaround still allows wrong integer-ID reuse.

### Explicit ownership model

- `attachment_store`: randomly allocated store UUID, PRIMARY-only discriminator, current random recordEpoch, monotonic generation, `feature_enabled DEFAULT 0`. Distinct PRIMARY installations/generations never share attachment paths or DEK envelopes. No DECOY medical feature or fake-note keys/indexes are introduced.
- `attachment_record_identity`: a stable, scoped UUID bridge to **an existing clinical row**, not a second visit/lab table. Composite PK `(store_uuid, record_epoch, record_uuid)`; typed `target_kind ∈ APPOINTMENT/LAB/DOSE_RECORD`, original `legacy_id`, state ACTIVE/TRASHED/PURGED, optional trash ID, 32-byte evidence digest. Identity columns immutable; typed existence checked on ACTIVE creation/restoration. Partial unique `(store, epoch, kind, legacy_id)` while not PURGED. Epoch is deliberately historical: FK is to store, not its currently mutable epoch; otherwise an epoch rotation would prevent quarantining historical links.
- `attachment_document`: scoped UUID, user-confirmed title/classification, CAS revision, logical trash/purge state/time, active version pointer. Composite active-version FK binds same store **and same document**, deferred for construction of the document/version pair. Insert begins with null active pointer; only verified version can be activated.
- `attachment_version`: immutable UUID/object UUID, ordinal, exact original-byte hash, plain/cipher byte counts, MIME and protocol revision, stable DEK handle UUID, verification/missing/corrupt/purged state. Object uniqueness per store and ordinal uniqueness per document. Content hashes are not dedup identity. Immutable content metadata blocks in-place replacement; replacement adds a new object/version then CAS switches pointer. Original file bytes retained.
- `attachment_link`: scoped UUID, recordEpoch+recordUUID FK and document FK, revision and ACTIVE/RETRACTED/QUARANTINED. Partial unique active association; no fuzzy date association. Active link creation/reactivation requires active identity in current epoch. Two identical original files may still be two deliberately different documents linked to different clinical events.
- `attachment_operation`: scoped operation and idempotency UUIDs; import/replace/trash/recover/purge/backup/fullrestore/oldrestore; phase; expected generation/document revision; pending resource reservations. Pending index enables recovery without scanning all originals. No filenames/URI are permanent references.

All new parent deletions are RESTRICT; no legacy FK/trigger/index is dropped or changed. Indexes cover current target lookup, document link state, version health, and pending operations. Every future Entity must declare matching Room `Index`/ForeignKey annotations and validate against a reviewed exported Schema10; CHECK/custom triggers must be installed on upgrade and every reopen, like existing SchemaGuards. Synthetic DDL uses no unbounded clinical BLOB.

### Required repository transactions (not implemented here)

1. B1 upgrade adds only empty attachment tables, creates random store+epoch, validates existing SQLCipher data/guards, leaves feature disabled. Create identities lazily **when explicitly linking**; this avoids guessing trashed historical payloads during migration. Future repository operations capture pinned store, lock/session generation and expected row revision.
2. Link create validates typed current row, current epoch, exact row expectation, document verified active version, active flags and user-selected identity within one `BEGIN IMMEDIATE` transaction. SQL constraints do not substitute for permission checks or live lock/session checks. `evidence_digest` detects accidental/stale payload differences; it is **not cryptographic authorization** against an attacker who can replace the encrypted database and keys.
3. Clinical delete writes existing trash snapshot, changes registry ACTIVE→TRASHED with existing trash ID and digest of canonical snapshot, and removes legacy rows in the **same** Room transaction. Clinical recovery first confirms exact trash+epoch+registry and no conflicting live row, uses existing parent-first reinsert, then changes registry to ACTIVE and clears trash ID; transaction failure preserves the trash/link graph. Identity never changes. These hooks are mandatory before any attachment feature enablement. A raw SQL active registry update cannot by itself prove snapshot continuity; the synthetic fixture verifies structural ordering only.
4. Purging a clinical row marks its identity PURGED, retracts/quarantines links with audit operation; objects remain if any other nonpurged document/link or retained version needs them. Reusing the same integer ID after purge gets **new recordUUID**. Never revive a purged identity to point to a new row. Clinical deletion does not mean permission to delete shared originals.
5. Document delete increments revision and marks TRASHED/time, preserving all original versions and associations for explicit recovery. Restore checks current epoch/targets/version existence/authentication, increments revision; missing target remains quarantined, not silently reattached. Purge is explicit permanent deletion after confirmation and full backup availability; mark PURGE_PENDING first, remove only unreferenced encrypted objects, then PURGED. Retain minimal tombstone/operation evidence; retention durations remain owner decisions.
6. Replace has durable reservation and new objectUUID+DEK; retries always allocate new crypto object, not reopen old ciphertext writer. Verified staged object is fsynced/renamed, then expected generation and document revision CAS switches active pointer. Historical versions remain until explicit retention/purge policy. A commit race never overwrites newer pointer.
7. Reservation check under one DB write transaction: sum verified retained objects + pending reservations, compare **candidate** quota; object count includes retained versions and pending objects, not merely document rows. Reserve ciphertext overhead and staging/free-space margin separately; 16MiB/256MiB/1000 are model proposals, not device acceptance. Abort drops reservation only after owned encrypted staging cleanup; crash recovery retains reservation until reconciled. SQLite CHECK only prevents negative values, not aggregate overcommit.
8. Operation phase CAS transitions PREPARED→WRITING→AUTHENTICATED→COMMITTED→CLEANED; precommit phases may→ABORTED. Only operation-specific transitions and idempotency key authorized by repository are allowed. The draft phase vocabulary is constrained, but **transition semantics and filesystem guarantees are not encoded/validated by DDL**; B2 must implement/test them.

### Restore / ID collision policy

Old PNBAK1 import must be refused while pending operations/readers exist, use existing backup validation, mint new random recordEpoch, quarantine all prior ACTIVE links, increment generation and replace structured records atomically. Same integer ID in restored legacy data cannot match historical recordUUID/epoch. Existing encrypted originals are preserved in quarantined recovery storage; reassociation requires explicit user selection and evidence comparison, never automatic date/ID/hash match. Production adapter must deliberately include attachment tables in the new whole-generation strategy; the current RawData domain-only importer must **not** execute unmodified over an enabled attachment library.

A complete new medical backup restores to a separate generation with original stable clinical identities verified against the package manifest; links resolved by scoped UUID, then actual target-row existence/type/evidence checked. Local target store UUID and Keystore key may change on new device: construct an explicit authenticated one-to-one mapping from archive scope to new local scope for metadata/AAD/key envelopes, or preserve the complete archived crypto namespace as a new isolated store. Do not rewrite authenticated object headers without re-encryption. Duplicate restore uses archive UUID+manifest digest idempotency and explicit replace/clone policy, not integer-ID merge. Final DB+generation pointer commit is the activation linearization point; user-visible success additionally requires reconciliation and durable completion receipt (report35); old generation remains available until durable reconciliation.

### Cross-review correction: key envelopes and physical generations

The initial frozen `key_envelope` field conflicted with KEK rotation. It has been replaced by immutable `dek_handle_uuid` in version metadata and a separate append-only `attachment_key_envelope` table: scoped envelope UUID, version FK+matching stable handle, monotonic candidate wrapping epoch, Keystore alias, wrapped DEK bytes, creation time, AVAILABLE/TOMBSTONED. New wrapping inserts a new envelope without rewriting original content, object identity, version metadata or protocol AAD. Old envelope bytes cannot mutate/delete and tombstones cannot revive. Repository authorization must ensure wrap epoch advances (unique SQL epoch alone does not impose order), decrypt+verify new envelope matches the actual old DEK, and keep old keys until new envelope durability/verification; SQL handle equality is not proof of equal key material. Deleted retired Keystore keys plus surviving encrypted envelopes do not guarantee forensic erasure or protection from full old-generation rollback. The fixture uses synthetic wrapped bytes, **not real Keystore wrapping or cryptographic verification**. A missing usable envelope blocks production access; this gate remains required in the live key service, not assumed from VERIFIED status.

`attachment_generation` now separates physical generation UUID (encrypted directory namespace), lifecycle STAGING/VALIDATED/RETIRED/PURGE_PENDING/PURGED, authenticated manifest digest and creation time from logical store/object/record identities. `attachment_store.active_generation_uuid` is a deferred composite FK; activation requires VALIDATED and increments numeric generation by exactly one. Caller supplies `WHERE generation=expected` CAS under transaction; stale CAS yields zero updates and no activation. Physical generation UUID **must not be in original-object AEAD AAD**, allowing identical authenticated ciphertext relocation into a new owned generation; logical store/object/version protocol identity remains authenticated; recordEpoch is authenticated in backup metadata, not original-object AAD. No replace-owned-directory or fsync durability is asserted by SQL.

Active-link creation/reactivation now checks both current active record scope and ACTIVE document with VERIFIED active version. Clinical trash keeps existing association rows; pending/trashed/corrupt/new documents cannot acquire new normal links. Query adapters still exclude quarantined/nonactive target/document/version. No active attachment reader remains valid after session or generation change; SQL alone is not a lock/revocation capability.

Added five tests: envelope append+old tombstone without version changes; bad handle/duplicate epoch/inplace mutation rejects; validated physical activation with exact generation increment and stale CAS; trashed-document link reject with retained original association; corrupt-version link reject. Original17 retained. Initial added envelope helper had one excess placeholder and failed2/22 before executing these test bodies; fixed helper only, no assertion weakening.
