## Conclusions / verified structure

For bounded, immutable synthetic objects, the POC has coherent authentication boundaries: JCA AES/GCM/NoPadding; 32-byte key, 12-byte nonce, explicit 128-bit content tags (ChunkObject39–44). New random DEK for each write attempt (54); prefix plus big-endian chunk sequence, reserved `ffffffff` footer sequence (37,81,90), no nonce reuse within one bounded write. Complete raw header is AAD with type/index/actual-length (38). Footer authenticates actual total, count and ordered SHA-256 (89–91). Reader authenticates footer, counts, exact physical length, every chunk and ordered digest before exposing bytes (114–132); random reads authenticate again and wipe whole requested response upon failure (134–157). Foreign identity rejection relies on **trusted expected identity** as well as AEAD, not on magic alone. Existing contract cases20–58 cover primitive known-answer, wrong key/identity, header/content/footer, truncate/trailing, reorder/duplicate/missing and cross-object splicing. They do not prove production integration, entropy quality, durable publish, all concurrency schedules, password attack resistance, or rollback protection.

### Findings and production blockers

1. **HIGH — revoke/publish check is not atomic.** ChunkObject94 checks authorization, then runs the RENAME fault callback and moves at95. A deterministic static counterexample sets `active=false` inside `fault(Stage.RENAME,...)`: file still publishes/Owned returns. The current cancel test changes active at BLOCK (contract65–69), which cannot cover this final boundary. Production must have a session/store-generation token and publish gate shared with lock/space-switch. Define the linearization: revocation winning the gate must prevent READY/link commit; commit winning it may retain authenticated cipher but must not expose content after revocation. Recheck inside the same gate as DB publish; file rename alone is not authorization commit. Regression: latch immediately before publish, revoke in another thread, release latch; assert no READY/link and no read capability; exercise reverse ordering too. **Static verified gap; new runtime reproduction NOT_RUN by this reviewer.**

2. **HIGH — owner close does not revoke existing readers.** Owned26–34 copies its key into each Reader; Owned.close zeros only its private copy. Reader102–104 owns an independent key and no owner/session token. `r=o.open(); o.close(); r.readAt(...)` continues to work by inspection. Existing contract79 closes r before o and therefore misses it. EncryptedPdfPoc has its own active/close wrapper (19,28–36,58–62), which mitigates that viewer path but does not fix generic Reader ownership or prove production lock integration. Production central capability registry/session generation must revoke all live readers, wrappers, native renderers, and returned cache handles; new open and byte-release check token, not merely a local closed flag. Regression exact sequence plus concurrent cross-block read/lock and already-decoded bitmap access. **Static verified gap; runtime NOT_RUN.** Best-effort JVM buffer clearing is not RAM-forensic erasure.

3. **HIGH — complete valid old-object replay is accepted by cryptography.** write accepts caller-supplied same Identity; test33–35 intentionally retries same identity with fresh DEK/prefix. Reader has no authoritative selected-version revision/recordEpoch/generation expected commitment beyond supplied Identity. A complete old object with its corresponding old envelope/metadata remains authentic. Distinct identities reject accidental cross-object swaps but do not reject rollback of the whole tuple. Production: generate a new immutable version UUID and fresh DEK for every attempt; authenticate protocol, logicalStoreUUID, documentUUID, versionUUID, operationUUID and generation context as appropriate; enforce selected active version/revision/recordEpoch in SQLCipher and read capabilities. Test restoration of an earlier valid file+envelope against a newer trusted metadata selection. **Important irreducible boundary:** rollback of the entire offline database, cipher store and any rollback state to a coherent old snapshot cannot generally be detected without an independent trusted monotonic anchor. Do not promise universal anti-rollback from AEAD or an encrypted SQLite counter. Keystore alias is not a universal portable monotonic counter. User-authorized old-backup recovery is a distinct explicit state transition.

4. **HIGH — authenticated file != crash-consistent database publication.** ChunkObject93 syncs file;95 atomic move; no directory fsync, durable operation row, READY transaction, generation-pointer ordering, owned-orphan journal or durable recovery cleanup. Catch97 ignores delete failures. Root53 tests symlink only once, not directory substitution/path race. Existing restart test proves a killed synthetic write leaves unusable part; it does not model power loss or durable directory entry after rename, nor production SQLCipher/filesystem atomicity. Production ordering: durable operation reservation → CREATE_NEW owned cipher → file sync → authenticate → same-filesystem rename → directory sync (verify API/device support) → gated SQLCipher READY/link commit → durable completion; crash replay must only remove operation-owned unreferenced paths. Failures must preserve previous selected version. Test every before/after sync, rename, DBcommit boundary; directory-sync failure, deletion failure, missing READY file, orphan committed file and restart reconciliation. Do not call arbitrary multiple copies atomic.

5. **HIGH — portable password wrapping is a test-only cost, not production design.** KeyEnvelope24–35 fixes PBKDF2-HMAC-SHA256 at100000, accepts any nonempty password; no encoded KDF version/budget parameters or production calibration; derives a key but JVM SecretKeySpec copies cannot be reliably erased. Context adds POC-PORTABLE-1 prefix; envelope contains salt plus nonce/tag/ciphertext. Wrong-password rejection is AEAD correctness, not resistance to offline guessing. Production independent envelope domain/protocol, authenticated bounded KDF parameters, random salt≥16B and vetted Argon2id implementation, password UX, fixed maximum pre-auth work, concurrency/cancellation limits and measured API26/29/35/ARM latency/RSS. Do not directly transplant RFC recommendations into Android without measurement, and do not change PNBAK1. RFC9106 contains separate 2GiB/t1 and64MiB/t3 profiles; those are external examples, not an approved phone setting.

6. **MEDIUM/HIGH — key-domain and per-key budgets are not a production contract.** Content perattempt new DEK, header/type AAD and reserved footer nonce are sound within the small POC. However keywrap14–17 accepts any SecretKey and arbitrary context; implicit provider tag length should be asserted128; contexts need canonical unambiguous encoding and separate roles (device DEK wrap, portable backup wrap, metadata manifest, content). Production may use independently generated keys or standard HKDF with explicit domain labels, never ad-hoc concatenation of variable fields. KEK reuse needs wrap-count/rotation policy and random96bit nonce collision budget; counts across backups/attempts matter. GCM budget must account for total authenticated blocks (ciphertext **and AAD**, footer and failed verification attempts), not just16MiB plaintext. POC at1KiB block allows≤16384 chunk encryptions plus1footer (81,127), everytag128 and maximum16MiB; this is a structural count, **not a quantified security theorem/certification**. Freeze conservative per-DEK invocation/byte limits and provider expectations; no resume or in-place update under old DEK. Inject deterministic randomness to test sequence exhaustion and retry key reset rather than probabilistically asserting two random values differ.

7. **MEDIUM — auth-before-open is a snapshot statement, not ongoing whole-file attestation.** Reader caches footer/header/hash after constructor; random block reauth ensures returned bytes are authentic. Same-length changes to an unread block or footer after open are not noticed while reading an untouched block. That is not unauthenticated plaintext leakage, but means “complete current file authenticated on every read” would be false. Production immutable object path + trusted version pin + no concurrent writers, authenticated FD ownership and invalidation must be specified. Re-run full verification if immutable object assumptions fail. Regression: alter footer afteropen/read untouched chunk, documenting expected reject-on-reopen vs immediateglobalrevocation policy. Avoid claiming the POC checks post-open footer integrity continuously.

8. **MEDIUM — cancellation can block; peak scratch formula is only an algorithm estimate.** Reader constructor114–132 scans the entire object with no cancel token. write checks active around source.read but a blocking provider read can stall forever; no timeout/descriptor cancellation contract (71–76). readAt144 serializes via Reader monitor, so close159 waits on in-flight block reads. Pdf render52 is native and cannot be assumed time-bounded by pagebitmaplimit. Production cancellable input fd, timeout/worker quotas, revoke token checked before plaintext release, bounded serialized verification tasks, validated parser worker isolation and complete cleanup are required. `maxScratchBytes=3*blockSize+16`113 excludes Cipher/JCA/native/VM internals and has no process-count/concurrency cap. Keep measured PSS separated from bound estimates; no ARM guarantee.

9. **LOW/MEDIUM — vector provenance and coverage incomplete for a new protocol.** Existing zeroAES256 vector contract20–23 tests standard primitive for one no-AAD16B case and roundtrip decryption, not canonical serialization, authenticated fields with nonempty AAD, multipayload boundary manifests, or cross-provider whole protocol vectors. Freeze deterministic synthetic draft vectors with key/nonce/AAD/plain/cipher/tag/manifest bytes, verify using an independent standard implementation and negative vectors that alter one field. Public primitive CAVP provenance must be verified rather than inferred from a familiar value. This reviewer attempted official NIST PDF/CAVP URLs and received HTTPError; no source fetch proof claimed. The draft protocol must keep a distinct research magic and never rename SYNPOC01 into production.

### Root's UNAPPROVED draft proposal — conceptual assessment

Proposed fresh256bit DEK + fresh object versionUUID + fresh salt each attempt; HKDF-SHA256 derives separate header/body/footer256bit keys using distinct fixed purpose labels and canonical header hash; body counter nonce; fixed nonce0 only under separate single-use header/footer keys. This is a reasonable **composition candidate for expert review**, not a security proof or approved protocol. HKDF is standard (verified RFC5869). Key separation removes cross-role nonce ambiguity only if keys truly derive under different canonical labels and each header/footer key is used for **one encryption invocation**. Changing a footer/known-length field in place with its existing derived key+fixednonce is forbidden; a new attempt has new DEK/version/salt and new derived keys. Retry/resume must never restore an old counter/key state.

Required definitions before implementation:

1. **No hash cycle:** define `canonicalHeaderUnsigned` as exact fixed-endian bounded bytes excluding authentication tag, with no optional ambiguous encodings, and `H=SHA256(canonicalHeaderUnsigned)`. Header key derivation may use H; header AEAD authenticates exact unsigned bytes (for an empty ciphertext header authenticator). Stored tag is excluded from H. Reader can derive from untrusted bounded header but must verify tag and compare trusted expected identities/version/epoch/hash before authorizing allocation or content exposure.
2. HKDF salt is a fixed32byte random field authenticated as part of header. Extract input DEK is exactly32bytes. Derive32byte keys with purpose labels encoded using a fixed-length protocol/version prefix + distinct enumerated purpose + fixed32byteH. Do not concatenate variable strings/IDs without exact framing. Header/body/footer purposes never reused for backup/metadata/device wraps. Derived key domains must be independent from old SYNPOC01 and independent full-backup format.
3. Body96bit nonce can be `0000000000000000 || uint32_be(index)` under a **fresh perobject derived body key**, not a globally reused key. Strictly increasing sequence0..255 in the proposed first profile; reject duplicated/missing/indexoverflow. Public random prefix is not necessary with genuinely fresh perobject keys, but omitting it remains a reviewed protocol decision. Footer/header allzero96bit nonce is safe only for distinct derived keys each used once. “Fixed nonce safe” must never be generalized to long-lived KEK wraps.
4. Perchunk AAD must bind H, domainpurpose, exactindex and actualplaintextlength. Footer authenticates actualtotal/count/orderedplaintextdigest, optionally exactexpectedcipherlength, and protocol commitment; exact EOF/no trailing bytes. Before preview authenticate header/footer/everychunk/orderedhash and compare trusted metadata commitment; perread reauthenticate pinned immutable version.
5. Hash of header alone does not establish trust or prevent coherent oldtuple rollback; selected metadata revision/epoch/version checks and explicit full-vault offline rollback limitation remain mandatory. Metadata plaintextcontenthash stays SQLCipher protected, not publicfilename/dedup index; explicitdocumentselection avoids clinical inference.
6. Test HKDF vectors independently (RFC5869 AppendixA), nonempty-AAD AES256GCM authoritative vectors, full positive/negative serialized draft vectors, and provider equivalence. Python independent implementation matching the same mistaken spec is evidence of interoperability, not independent cryptographic proof.
