## 3. P4-A：完成整个数据集的精确库存全局验证（最高优先级）

当前 `auditProjection(NotesDatabase, ReferenceScope, containerUuid)` 和 `auditStagedProjection(SupportSQLiteDatabase, datasetUuid, containerUuid)` 已共用只读 SQL，实现单容器审计；这是正确基础。**不要再维护第二套数值算法，不要把单容器成功扩写为全库成功。**

实施正式的、可在隔离暂存库中运行的**全局候选验证器**（名称按源码风格定）。输入必须来自可信当前 Schema + 解析过的业务数据，不允许执行备份提供的 SQL/DDL。它必须在任何目标数据集退休、旧数据删除、新快照写入之前完成全部验证。

要求一次性覆盖全部域，不允许“只验证有 CONSUME 的容器”：

### 3.1 基础输入与作用域

- 现有预算（大小、深度、数组、实体数、字段长度）、封闭字段集合、严格 JSON 列类型与不可变规范序列化。
- Room 版本与业务备份版本分别验证；来源数据类型和枚举严格；不允许把 JSON `true`、字符串数字、`NaN`、无穷数、`-0` 或科学记数法的歧义绕进库存值。
- datasetUUID、medicationUUID、recordUUID/revision、containerUUID、snapshot/event/operation UUID、外键、唯一性、CAS、请求摘要、来源版本/摘要及 epoch 关系。
- CURRENT 与 RETIRED 身份；退役身份下旧整数 ID 可以复用，但不得与新数据集或新包装混接。运行库的 preview/local epoch 不能从备份带入或被暂存库伪造。
- 没有官方许可或校验依据时只保留 `USER_ENTERED/UNVERIFIED`，绝不把它升级为 `VERIFIED_OFFICIAL`。

### 3.2 每个新模式容器的全历史

- 冻结包装内容、单位、成分、盐/酯/角色、有效数字/刻度、有向换算、实际可用容量来源、原始名义容量与来源哈希。
- 所有 CONSUME、REVERSE、ADJUST 的精确库存投影、符号、物理十进制量及有界整数；逐条前缀余额必须有效。
- 不用 SQL `SUM(Double)` 恢复精确总量。旧 Double 只能按冻结“整数刻度模式”的有界整数规则检查，单笔及余额限制 `0…2^53−1`，不得凭十进制字符串反推旧数据精度。
- 缓存与完整重放得到的精确结果分开：**先验证全历史，再确定是否允许在原子恢复中重建缓存**。审计过程不得自修复，也不得修改业务表。
- 确认包装名义 64 泵与用户实际可用 60 泵是不同事实；未知容量不可变成“库存有 64 泵”。

### 3.3 **全部**操作与相互覆盖

建立双向全覆盖：`measured_operation ↔ measured_allocation ↔ supply_transaction ↔ frozen presentation/reference ↔ actual confirmation / record revision`。

必须覆盖：

- 有消费且有分配的操作。
- 用户确认了真实用量，但因为容量不足、来源未知、单位不兼容而**无分配/未扣减**的操作；不允许当作 0 或自动补扣。
- 零差额 ADJUST、零效果观察以及没有 `supply_transaction` 行的操作。
- 多包装消耗及**完整跨包装逆操作集合**；不能只看到其中一盒完整就通过。
- REVERSE 的原消费指针、物理量、原冻结包装和准确的原分配量；不得用当前药物规格倒算。
- ADJUST 请求与执行锚分离：稳定 `request_sha256`、实际捕获 ledger head、零差额观察与重放；不能用墙上时钟代替因果顺序。
- 记录修订/删除/恢复的历史作用域、消费关联和只追加事件链。
- operationUUID 相同内容的幂等与不同内容冲突；不能有多余/缺失/孤儿证据。
- 旧 LEGACY_UNKNOWN 容器保持独立路径；历史未知不被悄悄升级。

### 3.4 负向测试（必须有真实拒绝结果）

至少故意构造并拒绝：孤儿分配、跨数据集相同整数 ID 串联、跨药物/记录修订、重复 REVERSE、缺另一容器的逆集合、无 CONSUME 的空来源操作、超范围刻度、类型伪装、零差额 ADJUST 缺因果锚、记录引用快照缺失、过期/冲突来源版本、错误方向换算、已作废包装消费、退役身份被当 LIVE、包装容量被名义次数替代、同UUID异payload、错误业务头版本、缓存与历史不匹配。

对缓存失配必须清楚定义：备份损坏的历史应整体拒绝；仅可重建的派生缓存不得作为“默默修好历史”的借口。每一个自动修复规则都需有充分证据，不能为通过测试而改变原始用户事实。

### 3.5 最低验收结果

- 单容器与全局校验使用同一换算核心/只读 SQL 或共享可信内部实现，不分叉。
- 全库审计运行之前/之后，源库和内存暂存库的业务表、触发器、FK、DDL 指纹一致。
- 新测试先在缺陷状态下失败并证明覆盖有效，再修至通过；禁止只做 happy path。
- 新增完整 JVM、真实 SQLCipher API26/29/35 合同；没有实际设备运行则记 `NOT_RUN`。

## 5. P4-C：接入真实服药事件和精确库存事务

已有 `MeasuredContainerStore` / `MeasuredConsumptionStore` 实现独立合成事务；现在要完成 **Repository 级真实生产调用链**，不能将独立测试方法当用户已经可以使用。

### 5.1 用户确认与单位

- 用户药物可以没有官方来源；用户手填包装规格合法，但永远是 `USER_ENTERED/UNVERIFIED`，不能因打包了 BDPM 参考档案就称官方核实。
- 必须显式确认本次实际使用的包装/容器（UUID）、原始用量、真实给药单位及有向转换依据；当前药物商品引用、mg 数字、单一候选容器均不能自动代表实际使用包装。
- 包装的容量来源区分 `USER_COUNTED`、`USER_DECLARED`、`LABEL_NOMINAL`、`UNKNOWN`；标签数量不能自动成为可用库存。
- 对旧数据、未确定包装、来源不足、量纲/成分不兼容，保留真实服药记录与明确未分配原因，不执行隐式新模式扣减，不回退旧 `SupplyLedger`。
- 对同一实际剂量跨不同规格拆分必须每份明确容器及来源；不能靠 FIFO 自动将 1 mg 与 2 mg 片拼剂量。同源兼容集合内可保留现有开封→密封顺序。

### 5.2 原子性与幂等

- 对新计量模式，实际服药记录 revision、来源捕获、measured_operation、measured_allocation、legacy ledger 整数投影必须在**同一数据库事务**中提交或回滚。
- 同一 UUID + 同规范请求重复执行无额外消费；同 UUID + 不同请求必须拒绝；跨数据集/药物/包装的重试不能误中。
- 成功记录后，后续引用更正不得重算用量、变更 record revision、运行 `saveMedication` resize、改变 PK 或计划。
- CONSUME/REVERSE/ADJUST 只追加，逆操作严格使用原冻结消费数量及包装身份；不能用当前规格逆算。原有 `PackageCorrections` 的 VOIDED/恢复 guard 不得放宽。
- 旧手动标量包装与旧历史维持旧路径；新计量包装一律禁止旧分配、resize、setRemaining、replace/discard 与旧冲销入口穿越（已有保护继续回归）。

### 5.3 观察、补录与 ABA

- 已有 ADJUST 因果锚仅证明数据库提交相对顺序，不证明现实世界的服药或实盘时间。不能拿时间戳判断是否已包含一次历史服药。
- 补录较早服药时必须明确区分“这次实际使用了多少”与“是否还需要减少当前库存”。可能已经计入稍后的人工实盘；若不能证明则返回 `UNKNOWN / NEEDS_RECONCILIATION`，不得重复扣减。
- 后来的独立实盘包含原消费时，自动逆操作必须拒绝并进入显式协调流程；较早实盘可按已验证因果锚规则处理。
- 确认票据除了余额，还应绑定数据集/容器/包装 revision、消费 ledger head、**零差额实盘也递增的观察版本**；ABA（余额改动后回到同一数字）必须拒绝过期票据。
- UI 取消、进程退出、确认中途失败无部分数据；调用方必须重新展示最新余额与原因再让用户确认。不要自动推荐剂量或治疗变更。

### 5.4 真正的调用路径

实现并测试：创建/确认新包装 → 服药完成或补录 → 精确扣减或已知未分配 → 编辑/修订 → REVERSE → 新 revision 重新分配或 UNKNOWN → 真实余量 ADJUST → 撤销/恢复 → 备份与恢复。测试必须调用正式 `NotesRepository` / production DAO，不是 debug test harness 的近似代理。

## 6. P4-D：用户可见的安全准入门

即使 P4-C 能写事务，如果正式库存页面仍可能将整数内部刻度当“片数”、将未知库存当0、或让库存提醒报告确定的可用天数，**仍不得启用正式入口**。

要么在 P4 中实现最小的、所有读取方共享的精确/旧制式/UNKNOWN 安全投影，并经四语/UI测试验证；要么继续保持新模式创建/消费入口 OFF，先在后续 P5 分支实现预测/UI，再统一开启。**禁止出现能够创建无法可靠显示、无法备份的新计量库存的正式发布构建。**

明确状态至少包含：已确认且可转换的库存、未确认容量/来源、单位不兼容、未分配实际量、不可预测原因；不得将未知视为零或充足。旧已确认标量库存不能因为新功能出现被重算。多包装只有可证明同量纲/同来源才能合并。

`StockForecast`、`StockAlerts`、库存页面、日历应读取同一统一结果。保持现有366日窗口、7日低库存（今日至第6日）、Europe/Paris 春秋 DST 日历语义，不能以固定 24 小时做跨 DST 日期判断。未来的 UNKNOWN 不自动触发医疗风险提醒。
