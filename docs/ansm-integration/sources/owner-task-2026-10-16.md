## 4. ANSM-02B：正式药品引用领域、历史、持久化和备份

### 4.1 用户与官方数据必须分离

明确四种不能混同的事实：

1. **参考药品**：BDPM 的源命名空间、CIS、CIP、成分角色、规格/剂型/途径、来源日期；不等同于用户的治疗方案。
2. **用户药物**：用户编辑的名称、实际剂量、途径、用药计划、既有 PK Profile；不能因为选中了官方商品就自动改写。
3. **当前关联**：某用户药物与某参考商品的 LINK/UNLINK/CORRECT；是用户选择的上下文，不证明每一条历史记录真的来自该包装。
4. **实际使用商品/包装**：只有用户为这条记录/容器**明确确认**时才成立；不能从当前关联、商品名、单一容器或 mg 数字倒推。

禁止将 CIS/CIP 塞进 `ProfileEntity`、`needs_review`、备注、未加密 SharedPreferences 或附件身份表来躲避正式迁移。

### 4.2 候选持久化结构（可优化命名，但不可丢失语义）

来自 `docs/ansm02/compatibility-design.md` 的候选概念：

- `ReferenceDataset`：当前/退役数据集、来源与本地 epoch；隔离备份恢复、整库替换及整数 ID 复用。
- `ReferenceMedicationIdentity`：稳定 medication UUID 与当前 legacy 整数 ID 映射、LIVE/PURGED，不能把 `active=false` 等同于已物理删除。
- `OfficialReferenceSnapshot`：不可变、规范化、带 SHA-256 的官方商品/包装字段及来源版本；即使当前目录不在也能理解历史；不能从后来目录重新解释旧快照。
- `MedicationReferenceEvent`：append-only LINK/UNLINK/CORRECT、UUID、修订、expected head revision、时间、上一个事件；重复 operation UUID 同 payload 幂等、不同 payload 冲突。
- `RecordReferenceCapture`：绑定到 record UUID/修订和当时引用 revision 的历史上下文；`actualProductSnapshot` 必须可空，默认 UNKNOWN，只有单独确认才存在；来源修订不得改变记录实际剂量 revision。

以上是设计方向，不直接照搬未经审查的 DDL。正式实施前给出字段表、键、FK、触发器、CAS 事务、规范化 JSON/摘要、尺寸限制、删除与恢复模型、Room 实际升级版本。

**Room 版本采用执行时真实下一版本**；不能因为旧方案写候选 Room11 就抢占别的开发者可能已经使用的 Schema。包括迁移和兼容测试、导出数据库 Schema JSON。不得破坏旧表或回填伪造官方身份。

### 4.3 数据操作 API

实现明确区分：

- search/list/detail 只读参考商品；
- link / unlink / correct 官方来源关联；
- set / clear actual-package confirmation；
- read current association and source revision；
- read historical captured reference independent of current catalog；
- errors: unknown product, missing source, stale CAS, identity mismatch, dataset retired, scope invalid, corrupt payload, duplicate op mismatch, invalid CIS→CIP relation, unknown verification/permission status。

要求：

- 事务内对预期 revision 做 CAS；两个编辑器竞争必须拒绝过时提交，不能 last-write-wins。
- 换商品时强制验证 CIP 属于 CIS；不能保留旧商品的 CIP。
- 取消/返回不能产生部分引用事件、容器 resize 或计划版本变化。
- 编辑当前引用不可更改旧 `MedicationSnapshot`、`RecordEntity.revision`、旧库存流水、历史 PK 快照或 PDF。
- 新关联默认只影响未来的显式捕获；**旧历史一律不根据当前关联自动回填**。
- 实际记录更正与引用更正是不同 revision 域，必须分别测试。
- 同一整数 medication/record ID 在不同数据集复用，不能导致跨数据集重新绑定。

### 4.4 迁移与旧数据

- 从原有 Room1→…→Room10 升级至执行时新版本；旧 1–10 fixture 批量覆盖。
- 原记录、药物、方案、库存及现有附件禁用基础元数据完整不变；没有官方来源的旧数据保持 UNKNOWN/null。
- SQLCipher 关闭重开、API26/29/35、DDL 任一点失败回滚、Room schema 哈希、FK/索引/触发器重装、完整账本不变。
- 老 APK 直接降级打开新 Schema 必须安全拒绝，不应静默删库；不承诺不受支持的降级。

### 4.5 PNBAK1 业务 schema 与恢复

**Room schema 版本与 PNBAK1 业务序列化 schema 是不同的数字。** 当前 Room10、PNBAK1 结构化业务 schema9 是历史基线；实际执行前核实是否改变。

保持 PNBAK1 现有外层加密封装和 KDF 不变。新增正式关联域必须完整列入 `DOMAIN_TABLES` / 显式列白名单、validator、writer、reader、clear/overwrite、恢复后触发器重装和 epoch 范围检查。新业务 schema 应按兼容策略独立增加，不要为了让旧版能读而谎称 schema9。

验收矩阵：

- 新版读取旧业务 schema1–9：原药物/库存完整，引用为空；不虚构 CIS/CIP。
- 新版本完整 roundtrip：包含所有冻结来源、关联历史和记录捕获；当前目录文件被移除仍可读历史。
- 旧 reader 读取新版本：在写入任何数据库前安全拒绝（NewerBackup），不得无声丢掉新域。
- 同库与不同库的导入：所有 UUID、record revision、container/medication 归属正确；不能仅按整数 ID 连接。
- 整库替换：退休旧 epoch、清除所有新旧引用、按正确依赖顺序恢复并重设 fresh 本地域；没有旧域遗留。
- 损坏、截断、超大、重复 UUID、孤儿、错误摘要、循环 revision、非法 CIS/CIP、缺失必要实际来源：严格失败并保留原库。
- 注入 `REVERSE` 和新表守卫/触发器情形：P0 已修复之后须确认与新表共存不再次失效。
- `RawData.unguarded` 后必须恢复**所有新旧相关守卫**；不得因为旧 `SchemaGuards` 不知道新表而留下 append-only 绕过口。

### 4.6 ANSM-02B 的明确完成标准

**不是写完 schema 即完成。** 必须能在正式 App（非 debug-only）中：查看药品参考、选择/解除/更正引用、重启保持、导出备份并恢复、查看旧记录来源状态，不改变现有用户用药事实。实际来源无法合法打包时，要用经过审查的非官方合成/用户自填路径验证完整生产接线，显式关闭未经批准的官方资源分发。

## 7. ANSM-03B：正式精确计量核心与包装快照

### 7.1 03A 原型生产化

从 #50 复用已经经过 35 项测试的精确十进制、有向转换、量纲/身份/证据与 UNKNOWN 语义。审计它在 test source 的公开构造、校验与域边界，再迁入合适的 `core/domain/src/main`，不要未经审查直接把测试文件复制到生产。保留全部旧测试，以同一组向量验证新生产实现与原型；最终尽量避免长期维护两套分叉算法。

至少支持并明确区分：

- 成分质量（mg、µg、g；含成分身份/盐/酯/水合物的语义）；
- 制剂质量（g 凝胶）与体积（mL）；
- TABLET、CAPSULE、PATCH、PUMP_ACTUATION 等离散单位；
- 包装名义总量 vs 经用户确认的实际可用数量；
- 贴片载药量 vs 标示释放速率；
- 已确认实际使用量 vs 给药计划量；
- 来源版本、冻结包装摘要和算法版本。

不得由 mg 直接转换 mL，除非有已核实浓度和化合物身份；不得用“商品名相同”替代同成分/同规格检查；不能把名义 64 泵说成实际保证能使用 64 次。对不能以受支持精度表示的值返回明确错误，不以隐式舍入造精确性。

### 7.2 统一容器与消费领域

参考 `docs/ansm03/production-integration-proposal.md`：

- 容器稳定 UUID + 当前 dataset UUID + 旧整数 handle。
- `ContainerPresentationSnapshot`：不可变来源、商品/包装/规格、原始成分、库存单位、名义容量与**实际确认容量**、有向换算关系、来源日期/算法/哈希。
- `ContainerPresentationEvent`：append-only LINK/CORRECT/UNLINK；有版本和 CAS；有真实消费后不可直接替换原快照。
- `MeasuredConsumptionCapture`：明确实际来源、输入量/单位、输出库存量、来源 relation、对应记录 revision/ledger transaction、逆操作和 operation UUID。
- 可恢复 dataset epoch、tombstone/永久删除边界，不能按相同整数 ID 错绑新容器。

实际数据库实体必须由 02B 和 03B 统一一次设计，尽量共享经批准的数据集/来源不可变机制，避免两个互相不兼容的“新 Room11”和两套备份 schema。不得复用功能关闭的医疗附件 crypto/identity 表来绕过明确迁移。

**旧库存不能自动迁移为“精确单位已知”**：保留旧标量和原余额，标为 LEGACY_UNKNOWN；不从当前名称、当前 unit、CIS、Profile 或数值猜测规格。除非用户针对未来某个容器明确确认，旧历史精度不能被重新发明。

## 8. ANSM-03B：正式 SupplyLedger 与库存预测接线

### 8.1 正式库存事务

仅在以下条件满足时允许新计量扣减：

- 实际容器身份由用户明确确认；
- 明确的商品/规格/单位/成分语义和冻结来源；
- 有向换算证据足够、数值有界且可计算；
- 当前库中容器仍有效，版本/CAS 未过期；
- 同一业务 operation 不重复分配；
- 该消费与用户原始实际记录在同一事务中完整提交。

顺序与现有逻辑兼容：**仅在确认兼容的同一规格/同一单位池内**，沿用开封日期/id，再未开封 id 的分配规则；不能跨不同规格自动“凑药量”。明确不足要保留真实的未分配量、原单位及原因。任何 UNKNOWN 不得被悄悄视为零。

### 8.2 关键业务操作

- `complete`/记录：避免双击重复扣减；内部 allocate 也必须按业务 operation UUID 幂等，不能只依赖 UI `complete` 的守卫。
- `correct actual record`：以原消费冻结单位和数量追加 REVERSE，再按确认的新来源建立 CONSUME；不按新商品规格“逆算”旧记录。
- `correct official reference`：只更新引用 revision，不改真实记录 revision、CONSUME/REVERSE、库存计划或 PK。
- `ADJUST`：方向、原单位、原因和操作身份明确；既有历史保留，不直接 rewrite used_amount。
- `VOIDED/restore`：保持既有 PackageCorrections 限制与完整账本哈希；已有消耗的容器不能靠新字段变相作废。
- 取消/失败/强停：事务原子；数据恢复时同一 UUID + 同一 payload 幂等，不同 payload 冲突拒绝。
- 并发：两窗口/两个重试/导入替换操作不得读取过时容器然后重复扣减。

### 8.3 过渡策略（避免破坏既有用户）

不能粗暴地“开启新算法后让所有旧药物库存归零”。设计双路径过渡：

- **Legacy 旧模式**：未获得新单位/实际来源确认的既有容器，保持原先经过验证的历史标量与兼容行为，但在新 UI 不将其声称为经官方核实的精确库存。
- **Verified 新模式**：只对明确确认并被冻结的兼容单位执行有证据的换算与分配。
- 两条路径不允许对同一消费同时扣减；应有明确且可测试的业务状态转换及防重入规则。
- 不允许 Verified 失败后静默回退成可能错误的旧标量扣减；给出 UNKNOWN/NEEDS_CONFIRMATION 和无部分提交的结果。

该策略必须同时照顾旧用户的可用性与新用户的可靠性，且必须在 PR 中说明什么时候可以退出旧模式。对于无法避免的行为变化，给出可复现的对照测试及可见提示。

### 8.4 统一预测和提醒

当前 `StockForecast` 将同药物标量加和；新设计不能把不同规格“片数”当成相同单位。统一返回：

- confirmed compatible stock groups；
- 每组经确认的可用量及单位/来源；
- 未确认容器及原因；
- 历史未分配真实量；
- 完整性/是否可确定覆盖到的日期；
- 缺失前提所导致的不可预测状态。

日历、库存卡和 `StockAlerts` 只用同一预测结果，不允许各自为政。证据不足时可展示保守的“已确认部分”，但不能宣称“肯定还够 X 天”；未知不等于缺货，也不等于库存充足；不能靠关闭提醒掩盖页面含义。

保留既有 366 日窗口、7 日提示、巴黎春秋 DST、跳过/覆盖/计划版本语义。任何改动应有旧/新基线对照；UI 四语明确“单位/来源未确认，需要人工核对”，不以医疗建议语气表达。

## 9. ANSM-02B/03B 的共享数据库与备份总设计

不要给 02B 和 03B 分别设计互相踩踏的迁移。**先合并候选实体与引用流，再确定单一、最小的生产迁移与单一业务备份版本演进。**

### 9.1 数据完整性要求

- append-only 引用历史、消费与来源快照不可修改；触发器对所有新表齐全。
- 稳定数据集+UUID 防止旧/新域整数 ID 复用串线。
- FK、索引、唯一约束、CAS、payload 规范哈希；来源快照必要事实随备份自包含。
- 当前目录丢失/更新/停产后，历史仍显示原冻结参考；从不按新版本静默重算。
- 旧 Room 表、既有账本与旧 MedicationSnapshot 保留；不修改旧用户“真实已服事实”。
- 历史快照的来源更正与实际用药事实更正分域，不能共用一个会冲销库存的路径。
- 新引用/消费表包含在 RawData/备份显式业务表清单，恢复删除顺序、守卫重建和退休数据集一并修好。

### 9.2 备份与失败恢复矩阵

至少覆盖：

| 测试 | 必须证明 |
|---|---|
| 旧 schema1–9 PNBAK1 → 新库 | 原业务不损坏；新引用 UNKNOWN |
| 新业务 schema → 新库 | 引用、快照、消费捕获、容器身份完整 roundtrip |
| 新业务 schema → 旧 reader | 在写库前明确拒绝，原库不变 |
| 目标库非空含 REVERSE | P0 修复后能按已定义语义完整覆盖恢复 |
| 备份没有当前目录 | 冻结来源仍可解释历史，无临时联网依赖 |
| 数据集 UUID/整数 ID 冲突 | 统一重映射或严格拒绝，绝无错误再关联 |
| append-only 触发器移除后 | 新旧守卫完整恢复，写入被正常拦截 |
| 中途失败、取消、磁盘空间不足 | 原库完整回滚，不显示成功 |
| 新程序崩溃/新进程恢复 | 不留下半完成数据与新旧 epoch 混合 |
| 备份过大/损坏/恶意字段 | 预算和关系校验先拒绝，不改现有数据库 |

不准把 `PNBAK1` 当成医疗附件正式完整备份：MED-02 的加密文件本体仍未启用。本任务只处理现有记录与本次 ANSM 引用/计量业务数据，不得顺便开启附件。

### 9.3 迁移及回滚

数据库从旧 1…10（及执行时所有真实版本）迁到新版本，真实 SQLCipher 上验证。禁止破坏性 fallback，禁止清库绕过错误。版本升级后旧 APK 降级不能自动打开新 Schema，提供安全拒绝；线上回滚用经过验证的修复前进版本，而不是删库强装旧版。

必须对 `RawData.restore` 的当前特殊行为、FK Restrict、触发器移除/恢复、DELETE 顺序、数据集退休和新域恢复作**统一代码审查**，禁止将两个各自可通过的局部修复拼成不一致的整体。

### 10.2 强停与断电测试的诚实状态

- 运行过的强停路径可标 PASS，但必须说明是哪个协议、哪个进程、哪个版本、具体断点。
- 真机 ARM、物理断电、用户手机升级安装和人为 TalkBack 没有实际测试就标 `NOT_RUN`。
- 不能把“新候选事务在模拟器成功”写成“全设备掉电安全已验证”。
- 可通过脚本自动完成的环境优先完成，不因为无真机就放弃所有其他工作。

### 10.3 CI 纪律

- 每个 PR 最终 HEAD 的六项必需 CI 都要真实成功，确认最新 SHA 和 GitHub checks；主线合并后须重新在合并 SHA 上验证。
- 出现失败先保留原始工件、定位根因；对网络/SDK/模拟器的纯环境故障允许少量有证据的原样重跑；原测试失败不得通过删除断言、缩小测试范围或随意延长超时蒙混过关。
- 明确 `PASS / FAIL / SKIPPED / NOT_RUN / NOT_IMPLEMENTED / BLOCKED`；不能借上一提交的绿灯声称最终提交成功。
- 记录 Gradle/JVM 限额、测试数量、失败记录、设备 API/ABI、artifact 哈希及源码来源 SHA。
