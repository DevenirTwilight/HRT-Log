Baseline: dc54c7fa / merged default320171cd. This comparison uses the actual full-audit source and preserved native reports, not a new latency claim. Schemas remain candidate13/business12 and default12/business11. No new schema version is allocated.

## Selection and implementation contract

For the current approved schema, **A remains the only fully implemented safe production mechanism**, but the existing frozen native results do not meet5s and its linear historical work is not a scalable solution. No new claim that further constant-factor tuning is impossible is made. The evidence does not justify another blind microoptimization cycle.

The selected structural direction to assess is **C: move an existing invariant into a database constraint**, rather than declare B's incomplete dependency closure trusted. The experiment is deliberately one proof boundary, not a new stock system or production authority. The zero-effect duplicate from B supplies the RED case. A SQL partial UNIQUE index on measured_operation(record_uuid,record_revision) WHERE kind='CONSUME' must reject that duplicate through the database writer itself, including raw/compiled inserts, and survive rollback correctly. It does not rely on a TEMP seal/counter cache. Existing frozen refutation tests remain unchanged.

This is insufficient for production admission by itself: a row can advertise a different legitimate record UUID from the one inside input_json. The constraint may accept it while the unchanged full auditor must reject it. That case must remain a negative test, not be patched away by trusting the row header. Consequently neither this one index nor a hash-chain checkpoint can replace semantic validation.

## Compatibility before any permanent DDL

The prototype installs and removes its index only in disposable synthetic test databases. It has no Room annotation, callback, APK code, new business table, trusted-state field or backup field. It must never be invoked from Repository/startup/restore. An index remains derived metadata, not frozen historical business evidence.

A future approved permanent index requires an actual negotiated Room version and identity hash, after checking current default/other database PRs. Migration must first run the independent full audit, then create the index in the same non-destructive transaction. A duplicate or inconsistent header rejects the entire upgrade, leaving the old encrypted database intact; no DELETE, repair, forced re-identification or destructive fallback. From-Room1 upgrade and old PNBAK1 import must reach that gate. Restore validates candidate rows before destination replacement and rebuilds the index, without serializing it as business data or changing PNBAK1 crypto. Any new persistent authority would need a separate business-version/old-reader refusal design; an old reader opening a newer Room version must fail, not drop/recreate. Downgrade means restoring an original compatible backup using a compatible reader, not opening a newer database with old semantics. Rollback tests must inspect both business rows and installed index state.

No standalone index makes arbitrary deliberate DDL tampering or physical corruption safe. A production authority would also need verified constraint installation, independently guarded write access and a documented corruption model. It cannot rely on app UI discipline, a mutable counter or a metadata existence check.
