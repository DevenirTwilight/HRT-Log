# 从复诊发展为医疗档案：长期产品方向

2026-10-08 产品决定；以 REQUIREMENTS §42 为准。

**状态：规划中，未实施。** 本轮只建立设计依据，不新增模块、附件库、数据库表、文件选择器或空页面。现有复诊功能继续保留。本文件中的阶段是建议顺序，不代表全部获准立即编码。

## 当前导航决定

撤销此前把复诊从侧边栏删除并合并到日历的决定。保留独立“复诊”侧边栏入口、现有页面、预约列表及全部功能，日历现有预约入口也继续保留；不移动、删除或重构导航。未来逐步扩展为 Medical Records / Dossier médical。只有医疗档案已有实际可用内容后，才考虑把侧边栏“复诊”更名为“医疗档案”，现在不更名。

## 产品定位与模块边界

医疗档案是 HRT Log 中长期保存、整理、关联和查找医疗资料的本地私密空间，不只是预约日历。

| 模块 | 职责 |
|---|---|
| 日历 | 安排和展示预约 |
| 历史页 | 查看实际用药记录 |
| 时间线 | 治疗时期及重要事件 |
| 化验页 | 结构化化验数据和采样上下文 |
| 医疗档案 | 保存医疗文件原件、管理就诊信息、关联上述既有数据 |

尽量复用稳定的记录引用和既有事实，不重复建立互不一致的数据副本。文件原件与结构化数据是不同对象；关联不能默认为自动改写或认可原文内容。

## 未来功能结构

### A. 预约与就诊

保留并继续发展已有预约、医生与地点、确认已就诊、就诊问题清单、回答与就诊备注、复诊资料包 PDF、既往就诊列表与记录。现有实现和剩余缺口见 [BACKLOG](../BACKLOG.md)，这里不将已有功能重新列为从零开发任务。

### B. 医疗文件

未来支持安全导入并管理化验单 PDF、医院检查报告、处方、病历和就诊记录、医生/医疗证明、医疗相关照片及扫描件。提供名称、日期、类型、可选备注。第一版不要求 OCR、全文搜索或自动识别；文件导入不自动生成或更改结构化化验记录。

### C. 医生和医疗机构

管理医生姓名、专业/科室、医院/诊所、联系方式和医院地址，关联相应预约与历史就诊。它不是社交联系人系统，也不是云端患者账户。复用现有就诊信息前先分析兼容性，不要求用户重新输入已有事实。

### D. 医疗资料之间的关联

- 原始化验单可关联一条或多条结构化化验记录。
- 一次就诊可关联处方和检查报告。
- 就诊可查阅对应时期的治疗方案。
- 复诊资料包可以引用用户明确选择的既有记录。

关联操作不得修改原始用药事实、冻结的化验上下文或已生成的历史 PDF；修改源记录也不能悄悄重写过去资料包。须区分实时引用和生成时冻结快照，并独立定义来源被删除/恢复后的展示与引用语义。

### E. 医疗记录摘要与导出

仅由用户主动选择时间段与资料，整理就诊信息、化验资料、用药方案变化、医疗文件清单及需要提供给医生的事实摘要。不自动诊断，不给药物剂量建议，不推断疗效因果关系；未知资料明确未知，不自动补猜。

## 文件存储与隐私：实施前必须验证的门槛

**SQLCipher 保护数据库，不会自动加密数据库外的 PDF、图片或其他文件本体。** 仅把原文件路径/URI 存入数据库，不能宣称已实现安全医疗档案。附件系统需要独立设计、威胁分析和可执行验证，至少覆盖：

| 门槛 | 需要设计并验收的内容 |
|---|---|
| 文件静态加密及密钥管理 | 文件原件独立加密；密钥生成、保存、解锁使用及生命周期；不把明文密钥与附件一起保存 |
| 访问边界 | 应用解锁、锁定、伪装模式下的访问权限和退出清理；伪装入口不得泄露医疗文件 |
| 离线查看 | PDF/常见图片离线读取与显示；不依赖远端服务 |
| 导入与临时文件 | 失败、取消、异常中断后的清理；明文临时缓存、外部文件选择器、预览和分享边界的泄露风险 |
| 资源上限 | 单文件大小、总容量、内存/解码/预览等资源限制；存储不足可恢复失败，不产生半完成引用 |
| 完整性与去重 | 文件校验、重复导入及去重策略；不未经用户决定合并不同医疗事实 |
| 稳定关联 | 文件与结构化记录稳定关联；导入、更新、删除、恢复和重启后无悬空/错配 |
| 删除语义 | 明确删除、回收站、恢复、彻底删除以及关联对象的行为；不能连带删除原始医疗事实 |
| 备份和恢复 | 文件、元数据、关联的一致加密备份及原子恢复；失败回滚、容量不足和操作中断 |
| 历史兼容 | 旧备份仍可恢复；备份格式版本演进、迁移/降级边界、缺失/损坏附件的处理 |

默认本地存储，保持离线优先和现有加密设计。不引入云账户、自动上传、分析 SDK 或新的网络权限。用户显式导出/分享需要另行定义范围和临时文件清理，不等同于自动上传授权。验收使用合成文件，不将真实健康资料、私密日志或身份信息提交仓库。

## 建议分阶段开发

每个阶段开始编码前，都需独立设计、兼容性分析和验收标准。下列最小验收方向用于后续设计，不能代替该阶段的完整安全规范。

| 阶段 | 范围 | 独立验收方向 |
|---|---|---|
| A：信息架构 | 复用复诊能力，确定医疗文件和关联模型 | 职责/导航明确，无重复事实；模型及删除/快照语义审查完成 |
| B：最小安全文件库 | PDF 与常见图片本地加密导入、查看、删除、备份恢复 | 加密与锁定/伪装边界、资源限制、失败清理、删除和完整备份恢复验证；旧备份兼容 |
| C：医生与医疗机构档案 | 管理医生信息，关联预约及既往就诊 | 保留已有就诊信息，编辑/关联/删除规则明确并测试 |
| D：跨模块关联 | 连接化验、就诊和文件，避免重复录入 | 一对多关联、源对象删除恢复、冻结数据及历史 PDF 不变性通过 |
| E：资料汇总与导出 | 扩展面向就诊的医疗资料整理 | 用户明确选取、事实摘要、未知值和来源准确；历史生成文件不被改写 |

进入阶段 B 前必须解决附件安全门槛，不以空页面或只有数据库路径的原型冒充实现。是否更名以及阶段授权，届时依据实际可用内容和用户决定，不由本文件自动触发。

## 当前不计划

- 云端电子病历服务。
- 未经用户明确授权与医院系统交换数据。
- AI 自动诊断或处方建议。
- 未经确认自动修改结构化化验数据。
- 将健康资料上传外部服务器。
- 为增加功能建立重复、相互矛盾的医疗记录。

## 本轮边界

Build 25/schema 9 保持不变；不改现有复诊数据，不添加医疗文件表、附件页或无实际功能的按钮。现有复诊、日历预约、问题清单和 PDF 功能继续保留。医疗档案的实现尚未开始；后续会话应先阅读本文件及最新 REQUIREMENTS/HANDOFF，再决定一个可独立验收的阶段。
