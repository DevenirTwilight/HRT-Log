# P1 第一批：方案版本、治疗阶段与统一时间线

2026-10-07。用户要求“下一阶段”，落实独立设计 II.1–2。当前基线734444a/build6/schema3。本批包含版本/阶段、统一时间线和用户里程碑；Lab Context/Visit Pack后续单独实施。仍使用既有正式签名交付，不改公开Release/标签，不改PK模型/当前体重政策。

## 问题与约束

schedule_rule服务提醒，名称/提醒阈值可变，不能直接称为不可变治疗方案。需要区分“当时记录了什么方案”“实际记录了什么”“同期有哪些化验/观察”。不自动推断疗效或因果；没有记录不意味着没有服药/症状。历史导入不强行匹配计划。日期记录不虚构发生时刻。

## 数据模型与独立实现

schema4新增regimen_version（稳定药物ID、UTC半开有效期、zone、definition_json、clinical_signature、origin、recorded_at_utc）、regimen_rule_link（旧schedule规则到独立方案版本）、milestone（用户选日期、类型、自填标题/备注）。方案definition冻结药物输入与周期/时间/剂量/锚点；关闭有效期是唯一普通更新。名称、包装、通知/提醒阈值不触发新的治疗阶段；途径/成分/酯/单位/剂量/周期/时间表/制剂PK输入改变才触发。提醒改动保持原周期锚点，避免为新提醒重置给药周期。

TreatmentEpoch是这些版本的确定性区间投影，不重复储存服药/化验，也不将推导结果冒充当时新录入的事实。边界是组合方案的变化，key由起点及成员版本ID组成，空方案间隙亦可显示；同时发生的多药变更只形成一个组合切点，无零长度阶段。起始HRT日期只由用户明确添加里程碑，绝不取最早数据库记录推断。

迁移3→4仅从旧规则及旧config_snapshot回推，标LEGACY_RULE、recordedAt未知，绝不用当前profile补历史；相邻同临床定义的旧规则合成一个版本。旧schema1/2/3备份恢复后同样升级，新schema4必须包含新表。现代备份验证新字段/JSON/关系/时间区间并失败回滚；所有新数据仍在SQLCipher中。

## 时间、观察与更正

实际服药按takenAt归于所在组合区间，关联旧计划的版本引用独立保留；不会因跨阶段服药截断PK残余输入。原始服药/来源snapshot保持不变。化验按sampledAt，预约按其明确时刻。daily/symptom/review/journal/milestone只有date时，按当前查看时区整日与各阶段交集展示；一天跨多个阶段须明确“归属不确定”，选择任一候选阶段可看到，不能直接统计成明确归属。界面显示当前查看时区。未覆盖的历史标“方案未知”，不补猜。

本批不开放回溯修改方案生效时间，不改写旧事件；时间线引用现有有效实体与revision，编辑/软删除后同步重建，不留下重复索引。也不声称保存完整模型bundle、复方强度或历史体重。

## UX

独立导航“时间线”，包含“时间线/治疗阶段”两视图。阶段卡显示日期区间、当时方案、回推标记；点阶段查看该区间事件。时间线按日期列方案变更、实际服药、确认漏服、未确认、跳过、化验、症状、每日状态/笔记、阶段回顾、预约、里程碑。过去自动未确认按日折叠；计划投影默认隐藏，可显示，明确与实际分开。支持范围、类型、药物、阶段筛选；观察原文与数值可展开，不解读化验。精简模式隐藏敏感标题/详情。

新增里程碑由用户自行填写/选择日期和类型，可编辑删除；方案/化验等现有事件不重复保存成里程碑。新增文案四语，沿用自身主题/导航，不复制竞品UI、代码、算法或文字。prior art是通用版本化/时间线思想，记录到PRIOR_ART。

## 验证

用合成数据验证：提醒/名称编辑不切阶段且不改变周期锚点；剂量/route/formulation修改切阶段；多药同刻组合无零长度/重叠；暂停/恢复/无方案间隔；旧snapshot未知和1→4、3→4迁移/旧备份升级；实际跨计划边界与date-only/DST候选关系；未确认不当漏服/计划不当实际；编辑/删除重建；新表备份往返与恶意关联/签名拒绝。跑JVM、data/reminder、app两变体、lint、四构建和原生CI，交付正式签名build7，注明真机未验证。
