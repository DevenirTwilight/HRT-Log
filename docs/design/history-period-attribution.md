# 历史记录按治疗时期归属，去掉错误的“计划外”（设计，待审核）

2026-10-08。依据用户本轮要求（REQUIREMENTS §35）及批复（§35a）与 [移交说明](../imported-history-plan-association-handoff.md)。基线 `fae435e`（build17，schema6）。**用户已于 2026-10-08 批复（见文末“批复结果”），按批复实施 build 18。**

## 0. 现状与根因（已在源码核实）

- `HistoryScreen.kt:201`：已服记录只要 `scheduled_utc == null`，就显示 `history_unscheduled_short`（“计划外”）。HRT Tracker 不导出原定时间（`HrtTrackerWriter.kt` 不写计划字段），应用内“手动记录”（`NotesRepository.unscheduled`）也没有计划时间。所以 build17 去掉导入徽标后，大部分历史都成了“计划外”。原始数据没有被改坏，错的是分类依据。
- `ObservedTreatmentHistory` 是只读投影，负数临时 ID 不落库，记录没有真正归属到任何方案。它判定新时期的隐含门槛是：7 天窗口内至少 3 天出现同一剂量模式、覆盖率 ≥ 2/3。所以“连续 3 天多吃”这种短期偏差可能切出新时期（尚未用测试验证，实施时先写失败用例确认）。这正是第二部分要交给用户定阈值的地方。
- `ImportedTimelineUiTest.kt:151` 断言“导入和应用内无计划时间都显示计划外”（`assertCountEquals(2)`）。这条预期本身是错的，要改（见第五部分）。

## 1. 数据模型

### 1.1 已确认的过去时期：新表，只追加修订

不复用 `regimen_version`，理由如下：

- `regimen_version` 不可修改，有同药物区间不重叠的触发器，`validateLinks` 要求它与提醒规则一一对应，而且它的 V1 签名已冻结在化验上下文和 Visit Pack 中。把推定方案塞进去，要么放宽这些保护，要么与已保存版本区间冲突。
- “确认 / 修改 / 撤销”需要保留历史，而 `regimen_version` 只允许关闭区间。

新表 `history_period_revision`（schema 7），只追加，不更新、不删除（触发器保证）：

| 字段 | 说明 |
|---|---|
| `id` | 自增 |
| `period_key` | 稳定 UUID：同一个时期的所有修订共用，确认后不变 |
| `revision` | 从 1 递增 |
| `state` | `CONFIRMED` / `REVOKED` |
| `medication_id` | 主药物 ID（多 ID 的同一身份见 `identity_json`） |
| `identity_json` | 冻结身份：成分、酯型、途径、制剂、单位 |
| `standard_json` | 当期标准：每次剂量的序列（不含钟点）、频率类型和次数（每天 N 次 / 每 N 天一次 / 每周 N 天） |
| `from_date`、`until_date`、`zone` | 本地日期区间 `[from, until)`；`until` 为空表示一直延续到下一个已保存方案或今天 |
| `evidence_json` | 推定依据：识别器版本、所用阈值参数、来源记录 ID 及其 revision、日数与次数统计、用户改动了哪些字段 |
| `origin` | 固定为 `OBSERVED_USER_CONFIRMED`（界面文案：“由记录推定，用户已确认”） |
| `created_utc` | 写入时间 |

- 当前状态等于每个 `period_key` 的最新修订。修改：追加新修订（仍是 CONFIRMED）。撤销：追加 REVOKED 修订，该时期回到“未确认候选”。不删除任何行，也不改动任何原始记录。
- 只保存日期区间和标准。**不生成提醒规则，不写入** `scheduled_utc`、`slot_key`、`rule_version_id`，不保存负数临时 ID（证据里只存真实的记录 ID）。
- 同一身份与标准、区间相邻或重叠的已确认时期，在确认时提示合并。导入日期或来源不同不构成拆分理由。
- 和已保存方案（`regimen_version`）的关系：已保存方案优先。已确认时期的显示区间截到第一个已保存版本之前；如果两者标准相同（V2 相等），时间线上合并显示为一个时期（沿用 build17 的连接规则，不跨过不同的保存版本）。

### 1.2 用户明确标记的“额外服药”

新表 `record_annotation`（schema 7）：`record_id`、`kind = 'EXTRA'`、`created_utc`，主键 `(record_id, kind)`。这是对记录的附加说明，**不改 `dose_record` 行**（实际时间、剂量、revision、库存账本都不动）。取消标记即删除这一行。

入口有两个：
- 历史记录菜单里的“标为额外服药 / 取消标记”；
- 手动记录服药对话框新增可选勾选“这是额外服药”，默认不勾。

### 1.3 归属与标签：实时投影，不落库

记录属于哪个时期、是否“额外”、是否“剂量与当期不同”，每次在读取时计算，不写库。

- 好处：记录可以编辑、软删除，时期可以修改、撤销，导入可能重复。投影是确定性的，修改后自然重新计算，不会留下过期关联，也不需要失效逻辑。按现有规模，计算量很小（每药每天几条）。
- 代价：每次刷新都要计算。可以在 ViewModel 中按数据快照缓存。
- 位置：纯函数放在 `core/domain`（新 `PeriodAttribution`），输入为记录事实、已保存版本的 V2 标准、已确认时期、用户标记；输出每条记录的归属与标签。History、时间线、复诊资料包、CSV/PDF 共用同一函数。

### 1.4 History 标签规则

只看“已确认时期”和“应用内原本保存的方案”。有原定时间的应用内记录，准时/迟服/漏服的判断保持现状，以下规则只用于没有原定时间的记录。所有来源（应用内、HRT Tracker、Trans Memo）规则相同。

| 情况 | 标签 |
|---|---|
| 落在时期内，药物、途径、剂量都符合当期标准 | 无标签 |
| 没有原定时间 | 不判断准时/迟服，也不显示“准时” |
| 当天记录数多于当期每天次数 | 多出的记录标“额外（推断）” |
| 用户明确标记 | “额外”（不带“推断”），优先于推断 |
| 单条剂量不在当期标准的剂量集合内 | “剂量与当期不同”；不切时期 |
| 当天记录少于标准 | 无标签；不算漏服，不推断停药 |
| 找不到所属时期 | “方案未知” |
| 只落在未确认候选时期内 | 见下方建议 |

**“额外（推断）”标哪一条（建议）**：同一药物同一天（按记录自身的时区取日期），按实际服药时间排序，前 N 条（N = 当期每天次数）视为正常，从第 N+1 条开始标“额外（推断）”。理由：可预测、不依赖剂量猜测，用户看到的说明是“当天第 3 条，超过每天 2 次”。另外，当天已有用户明确标记的额外记录时，先把它们排除，再计数，所以明确标记的那条不会让另一条再被推断成额外。

- 备选 A：只在当天整体标注“本日多 1 次”，不点名哪一条。最诚实，但历史列表里看不出是哪条。
- 备选 B：剂量与当期不同的那条优先标额外。容易把“剂量不同”和“额外”混在一起，不建议。

**剂量判断**：每条记录的剂量与当期标准中的剂量集合比较（单位必须相同，不做单位换算猜测；容差为浮点误差）。标准是“早 1 mg、晚 2 mg”这类不均匀分配时，因为不保存钟点，无法知道某条属于哪个时段，所以只要剂量在集合内就算符合。当天两条都是 2 mg 这种“组合不同”是否要标，列为待决定第 4 条。

**每 N 天一次或每周 N 天的方案**：因为相位（锚点）不属于标准，无法判断某天是否“不该服药”。建议只标“同一天超过 1 次”的额外；两次服药间隔明显短于 N 天的情况，列为待决定第 5 条。

**未确认候选时期**（用户要求我给意见）：建议**也去掉“计划外”**，但不做“额外/剂量不同”推断，只显示中性的“待确认时期”，点开可跳到确认页。理由：“计划外”是一个明确但错误的判断，比不加标签更误导；而“额外/剂量不同”依赖的标准尚未经用户确认，所以不应该推断。

## 2. “长期变化”的判定方案（阈值由用户决定）

所有方案都只用于**提出候选边界**，最终由用户在确认页决定。下表的 D、K、W、p、G 是待定参数；括号里是用来比较的示例值，不是建议值。

| 方案 | 规则 | 短期加量后恢复（加量 3 天） | 慢慢减量（每档 5 天：2→1.5→1→0.5 mg） | 长时间没有记录（30 天空白） |
|---|---|---|---|---|
| O1 固定天数 | 新模式从第一天起连续保持 ≥ D 个**日历日**（中间缺记的天不打断，但出现旧模式就打断）（D=7） | 不切；3 天都标“额外” | 每档只有 5 天 < 7，不切。整个减量期留在原时期，几十条“剂量不同”，不理想 | 空白期不算新模式也不算旧模式；空白后恢复原模式则延续 |
| O2 记录天数 | 新模式出现在 ≥ K 个**有记录的日子**，期间不再出现旧模式（K=5） | 不切 | 每档 5 个记录日，刚好切出 4 个短时期 | 同 O1；稀疏记录时比 O1 更难达到门槛 |
| O3 窗口占比（当前算法属于此类，W=7、至少 3 天、占比 2/3） | 任意 W 天窗口内新模式占有记录日 ≥ p，且至少 n 天 | 当前参数下**可能会切**（3 天满足“7 天内至少 3 天”），与用户规则冲突；调高 n 或 W 才不切 | 视参数而定，可能切成若干段 | 空白不计入分母，可能把空白两侧连成一段 |
| O4 持续到下次变化 | 新模式一直保持到下一个不同模式出现，并且 ≥ D 天才切；否则视为偏差 | 不切 | 每档都“保持到下次变化”但都短于 D，不切；与 O1 相同 | 同 O1 |

**长空白**：任何方案都不从空白推断停药。建议另设参数 G（例如 14 天，由用户定）。空白 ≥ G 时，空白两侧拆成两个候选，即使标准相同，确认页提示“与前一时期标准相同，可合并”。空白 < G 时，视为同一时期内少记。

**慢慢减量**：上述方案都不完美。可以在确认页把连续的短时期显示为一组“逐步调整”，让用户选择“合并成一个调整期”或“分别确认每一档”。这只是显示方式，不改变记录。

识别结果只是候选。确认页可以调整起止日期和标准，所以阈值判断不准时，确认环节兜底。

**文案思路（四语）**：

| 中文 | 繁中 | 英文 | 法文 |
|---|---|---|---|
| 额外（推断） | 額外（推斷） | Extra (inferred) | En plus (déduit) |
| 额外 | 額外 | Extra | En plus |
| 剂量与当期不同 | 劑量與當期不同 | Dose differs from this period | Dose différente de la période |
| 方案未知 | 方案未知 | Regimen unknown | Traitement inconnu |
| 待确认时期 | 待確認時期 | Period to confirm | Période à confirmer |
| 由记录推定，用户已确认 | 由紀錄推定，使用者已確認 | Inferred from records, confirmed by you | Déduit des prises, confirmé par vous |

- 语气中立，不评判、不给剂量建议。
- 精简模式：药名照常隐藏；确认页只显示途径、频率和剂量，不显示药名。标签照常显示，因为它们不含敏感名称。
- 按钮大小遵守 REQUIREMENTS §29。

## 4. Schema 7 迁移与兼容

- `6→7`：只新建 `history_period_revision` 和 `record_annotation` 两张表，以及索引和守护触发器。不修改任何已有表和行。
- 备份：两张表加入 `DOMAIN_TABLES`。schema 1–6 的旧备份恢复时没有这两张表（视为都未确认、没有标记）。schema 7 备份必须包含它们。恢复时校验 JSON 结构、日期、`state` 取值、修订编号连续、`record_annotation.record_id` 外键，失败整体回滚。
- 旧安装直接覆盖升级，不需要卸载或重新导入。升级后所有历史仍按现有投影显示，只是不再出现“计划外”。确认是用户之后的主动操作。
- 不改动：原始记录（时间、剂量、时区、来源 key、冻结快照）、库存账本、化验上下文、Visit Pack、V1 签名、PK、公开 Release 和标签。

## 5. 修正错误的测试预期

`ImportedTimelineUiTest.importedAndAppHistoryHaveTheSameUnplannedTimestampPresentation` 改为：

- 同一合成场景下，HT 导入记录与 APP 记录都**不出现**“计划外”文案（不再期待 2 个）；
- 在已确认时期内且符合标准时，两条都无标签；没有任何时期时，两条都显示“方案未知”；

`history_unscheduled_short` 这条文案只在确实需要时保留（例如应用内带原定时间的槽位被用户改成计划外的旧数据，见待决定第 7 条），否则删除。

## 7. 与之前决定的冲突或需要用户决定的地方

1. **长期变化的判定方案与阈值**：选 O1 / O2 / O3 / O4 之一（或组合），并给出 D、K、W、p 的数值，以及长空白阈值 G。注意当前算法（O3：7 天内 3 天）可能把短期加量切成新时期，与本轮规则冲突。
2. **“额外（推断）”标哪条**：建议按时间先后标第 N+1 条起；或改为只做当天整体标注（备选 A）。
3. **未确认候选时期**：建议也去掉“计划外”，显示“待确认时期”，但不推断额外和剂量。是否同意？
4. **非均匀剂量的组合**：标准“早 1 mg / 晚 2 mg”，某天记成两条 2 mg。每条都在集合内，是否要在当天标“组合与当期不同”？
5. **每 N 天一次的方案**：除“同一天多于 1 次”外，两次间隔明显短于 N 天（例如每 3 天一次的方案，隔天又服）是否也标“额外”？
6. **逐步减量**：是否需要“逐步调整期”这种分组显示，还是每一档都单独确认？
7. **“计划外”文案的去留**：应用内带原定时间的槽位不会出现这个标签。是否完全删除这条文案？另外，现有的手动关联导入记录到槽位（`linkImported`）功能是否保留？它与本设计不冲突，但两套入口可能让人困惑。
8. **与 REQUIREMENTS §30 的关系**：§30 要求“可靠匹配的历史直接进入治疗时期”（无需确认）。本轮要求推定方案确认后才保存。建议：时间线仍可显示自动识别的时期，但标为“待确认”；只有确认后的时期参与 History 标签和复诊资料包。这样修改了 §30 的语义，需要用户确认。
9. **化验上下文**：已确认的过去时期，是否在之后**新建或重建**的化验上下文里作为“采样时所属时期”出现？已冻结的化验上下文不受影响。
10. **复诊资料包和 PDF**：是否在“服药记录”里使用新的标签（额外、剂量不同、方案未知）？建议使用，并写明“由记录推定”。
