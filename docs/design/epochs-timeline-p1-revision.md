## 一、里程碑“开始激素治疗”保存后没反应：根因

### 复现（合成数据，Robolectric，本地探针测试，未提交）

| 步骤 | 结果 |
|---|---|
| 时间线 → 添加里程碑 → 类型选“开始激素治疗” → 保存 | 保存回调触发，`kind=STARTED`，按钮可用（`enabled = kind!="CUSTOM" \|\| title非空`，STARTED 无需标题） |
| ViewModel `saveMilestone` → `repo.saveMilestone` → `dao.milestone(@Upsert)` | 数据库中有该行，`state.error` 为空，无异常 |
| `LongitudinalProjection.build` | 产生 1 条 MILESTONE 事件 |
| 时间线页面：日期为 10 天前 | 显示 |
| 时间线页面：日期为 400 天前 | **不显示** |
| 切到“治疗阶段”视图 | 任何里程碑都**不显示** |

### 结论

1. **根因**：保存成功，但被时间线的显示筛选挡掉了。时间线默认只显示**最近 90 天**（`LongitudinalScreen` 中 `days` 默认 90）。“开始激素治疗”通常是几个月或几年前，日期一早于 90 天就被过滤；最近N天筛选还会过滤未来日期（开启显示计划可解除未来限制，或选择全部时间绕过日期条件）。另外“治疗阶段”视图只列阶段卡、从不列里程碑，而“添加里程碑”按钮在两个视图都显示。
2. **为什么像“没反应”**：对话框照常关闭，没有任何保存提示，列表又没有新条目，看起来就像点了没用。源码与合成证据不支持将它归因为STARTED写库约束；不能据此保证用户那一次实际写入结果。
3. **层级**：确认的缺陷在UI层（时间线的显示筛选与反馈）；合成路径的数据层正常，未检查用户真实数据库。表上没有唯一性约束；触发器只检查日期长度、类型取值、CUSTOM 需要标题，STARTED 不受影响；协程异常会进 snackbar，本例没有异常。
4. **最小修复**（审核后实施）：保存或编辑里程碑后，如果它落在当前筛选之外，等待写库成功后关闭对话框，显示“已保存”及“查看”动作；查看时显式扩大范围、清除不兼容类型/阶段筛选并定位该ID。失败保留输入；保存已成功但刷新失败应区分提示，避免重复写入。保存结果需返回新ID/状态，增加处理中与防双击。在第二部分的新时间线里，所有阶段和里程碑都会列出，这个问题从结构上消失；是否先单独实施最小修复，由用户审核决定，本轮不实施。
5. **回归测试**：日期在 400 天前的 STARTED 保存后可见；从“阶段”视图添加后可见；编辑日期、改类型、删除；未来日期的处理（见“待决定”第 10 条）；ViewModel 重建（模拟进程重建后从数据库重新读取）仍可见；STARTED 日期只来自用户输入，不由最早服药记录推断（已有行为，保留断言）。

## 二、治疗标准签名与存储签名分离

### 现状与不能直接改signature()的原因

`RegimenDefinition.signature()`（RegimenHistory.kt:22–40）含钟点、相位和时区。`changed()`按此签名存方案行，`TreatmentEpochs.build`按成员版本ID组合区间，因而提醒变化产生临床阶段碎片。`saveMedication`的`samePlan`与`cadenceUnchanged`也用时间/签名保证提醒语义，不能替换成忽略钟点的临床比较，否则可能漏更新提醒或错误重置周期。

现有`clinical_signature`实际承担v1完整指令指纹：BackupValidation.kt:89–94要求definition.signature等于该列，并调用validateLinks（RegimenHistory.kt:73–76）校验每条规则的指纹。直接改算法会让合法旧备份失败；触发器也禁止改已有定义、签名和链接。

**推荐：不改原signature()的字节语义，不改已有行或链接，新增仅用于投影的therapySignatureV2。** 可将旧函数明确注释为legacy storage signature，但保持API/输出兼容。完整指令版本仍可细分，临床时期合并它们；用户确定的是“不切阶段”，不是“提醒变更绝不保留版本”。无必要增加表/签名列或迁移当前schema6。

### V2标准的候选结构（独立定义，未实现）

| 字段 | 比较方法 |
|---|---|
| 药物身份 | 纳入稳定medication_id，换药/增加/停用改变组合；名称不纳入。不根据品牌字符串猜化学身份 |
| 已知成分/酯型/途径/单位 | 使用版本中的已知值；缺失用明确unknown，不从当前profile补。单位不凭空折算 |
| 制剂 | 明确凝胶product ID、贴片规格/释放速率。名称不是制剂字段；现有模型没有完整厂家/浓度/复方身份，不能声称全覆盖 |
| 频率 | kind、interval、每周期给药次数；每日次数取times长度，每周天数取weekday mask位数（具体星期几待定）。hours型用小时间隔，不因锚点/相位不同切阶段 |
| 剂量分配 | 取每次实际指令量dose_override ?: dose，按已有时段顺序组成向量，包含次数/单位；不包含钟点。不能只用总和：[1,2]和[2,1]总量相同但分配不同 |
| 每天总量 | 每日型由剂量向量求和，保证总量变化能检出。每N天/小时/周不虚构固定“每天总量”，保留其频率和每周期剂量 |
| 排除 | 钟点、时区、锚点、名称/包装/库存、提醒/通知、实际服药状态、当前体重/化验校准等PK设置 |

编码采用固定字段顺序、version=2、显式空值与有界有限数值；摘要用于确定性比较，不称医学等效。未确认规则不塞入默认医学假设。

剂量分配有一个数据限制：现有rule_time没有稳定“早/晚”时段ID，只存具体时间。通常可按时间排序后取剂量序列，但当用户把一个提醒拖过另一个提醒导致排序翻转时，无法仅凭现有字段区分“改提醒”与“交换分配”。建议交互明确确认是否交换分配，必要时后续新增时段身份；本轮不做隐性迁移。既有每时段覆盖量不能在普通提醒编辑中丢失；saveMedication目前会重建null覆盖的时间行，需要实施时专门防回归。没有明确早/晚标签的历史不能擅自显示“早/晚”，显示“第1次/第2次”。

### 投影结构

- `RawInterval`：保留原UTC半开区间、原版本ID和冻结定义，服务历史审计/采样精确上下文。
- `TreatmentStandardSpan`：同药、首尾相接且V2标准相同的原版本合并，保留全部sourceVersionIds。未知身份不跨药物合并。
- `ClinicalSegment`：对治疗段的精确边界作多药组合，只在标准组合变化时分段；原始分钟边界不写回数据库。
- `DisplayPeriod`：按日期展示ClinicalSegment，含标准、原精确子区间、sourceVersionIds、变更日信息、条目引用。所有同日临床变更显示一次切点，普通提醒变更不产生切点。

保留旧TreatmentEpochs.build作为legacy精确构建入口供现有冻结快照格式使用，新增独立V2构建入口/DTO，避免给旧消费者悄悄换含义。对组合标准比较不能只比较“累计所有版本ID”，否则提醒改动仍会切阶段。

## 三、日期展示、同日变更与key

### 日期与真实时间分离

不把存储的UTC边界直接取整到午夜。推荐使用一个固定、明确的时期分组时区（可取最早已知方案的保存时区并显示），不随提醒时区或设备旅行自动改变。不能逐版本使用不同zone后组合，跨区会产生错序/重叠；也不能因设备时区变化而把原同日组拆成两期。固定分组时区及选择入口待审核；它是日期展示政策，不纳入治疗标准签名。导入更早历史或用户明确更换分组政策时，重新投影并标识政策变化，不声称治疗标准改变。

普通时期按日期显示。后继阶段恰好从当地午夜开始，前阶段显示至前一天；若当天内发生临床调整，日期卡需标明“方案变更日”，不能宣称从当天零点已服用新方案。已确定的“多药同日只切一次”采用显示聚合：同日的多次变更折叠为一个过渡组，以当日最后明确保存的组合标准作摘要，注明“当日最终记录方案”，保留中间精确片段。

变更日化验/预约按发生时刻仍解析到正确精确片段，但作为当天时期条目显示；日期型回顾/里程碑归入变更日，并保留归属不确定标记。这样只显示一个日期切点，又不把上午的样本解读为下午的用药方案。该过渡日表现方式待审核；不能自行采用旧稿“全天新方案”的假设。同日停用/恢复及一日内A→B→A不能悄悄抹去真实调整，过渡组保留历史，和相邻纯稳定日合并需受待定恢复规则约束。

### key与引用

- legacy key `epoch:<毫秒>:<版本ID集>`保留为原格式，不删除、不冒充V2时期ID。
- 新key建议 `period:v2:<固定分组时区>:<首个真实临床边界UTC>:<标准段首版本ID集>`，不用屏幕上第几个阶段、结束时间、或持续加入的提醒版本列表。同标准追加版本延长时期但key稳定。
- 同日变更key由该日期过渡组首个真实临床边界和政策版本确定；首版本ID用于确定锚点，不作为临床标准是否相同的依据。
- 原版ID→多个新组合阶段是正常情况：一味药没变、另一味药变化时，它的同一版本就跨多个阶段。旧epoch→新时期也不是保证一对一。建立带时间范围的映射 `(legacyKey/sourceVersionIds, sampledAt/日期) → candidates`；优先精确时刻，日期或历史缺失时可有多个候选/unknown。
- 政策版本/明确选择的固定分组时区不同产生不同投影key是可解释变化，不是历史记录ID变动。UI恢复旧筛选失败时明确回到全部时期；不可落到相同index的另一个阶段。真正历史更正可改变投影，不能承诺所有未来政策都不变key。

**Lab Context具体风险**：当前validate要求version=1，且epoch key等于from与活跃版本ID组合，regimens每药最多一条（LabContext.kt约42–57）。直接把新key/日期塞入旧epoch会拒绝合法记录。推荐本次不变JSON协议；只新增独立“按当前规则对应时期”的展示映射，按sampledAt而非孤立版本ID匹配。旧引用存在时原ID仍可解析；如果备份、删除/整体恢复造成引用不在当前库，冻结definition仍可读，标关联未知，不能承诺外部引用永远存在。重建也保留原版本并标清捕获时刻。

如以后要冻结V2时期，应另行设计context_version=2、独立display_period/政策字段和旧新分支校验，不能把V2含义装进version=1；同一JSON列不要求Room迁移，但旧APK不认识新载荷，回滚/备份读取也必须有兼容计划，不在本次默认批准范围。

**Visit Pack已实现**：schema6有visit_pack，VisitPack.kt存template_version=1、区间、语言/时区、勾选项、input_digest与facts_json；没有冻结epoch key。事实regimen_started/ended计数来自原始版本边界，而REGIMEN部分PDF/摘要输入保留原版本。这些是版本事实，不是临床阶段改变次数。若用户选择template2：另加有政策标识的治疗标准变化计数，不复用旧键的新含义；同日多药变更一次，首次“记录可知”不伪装成HRT开始，未知历史不报确定次数。更新VisitFacts/factLines/VisitDigest、PDF排版与四語，模板版本参与新digest；新增生成行，原digest/facts/PDF不变。原PDF正文未存DB，不能用今天数据重新生成后声称是原文件。

**迁移/恢复/回退**：推荐第一批schema6不变、不增表、不重写行。schema1–6备份仍走原恢复流程与预算/全量校验，恢复后显示投影重建。验收要对已有行/原JSON作逐字段相等检查。撤回V2显示采用向前发布保留兼容读取的修复，不建议用户安装旧APK；没有schema降级需求。若时段ID/制剂身份将来需新增schema，那是另批设计、先加可空字段、不猜补旧值，迁移前备份并以保留新格式读取的向前修复回退，不能承诺任意旧APK可读。

示例数值仅是用户提供的展示例子，不是模板或推荐。不能从品牌补推制剂。时段剂量不同时显示第1次/第2次，未知量或频率直接注明；不把当前名称/配置替换历史定义。卡片内只有日期、类型、标题；化验结果、回顾全文、预约地点和里程碑备注进入专用详情，不展开在卡片。允许类型为LAB/REVIEW/MILESTONE/APPOINTMENT，条目source ID与date/instant均保留，不能只跳到模块首页而不定位。精简模式隐藏药名/剂量/途径、项目和用户标题/备注，仅中性日期与类型；成功提示也不泄露敏感内容。

“方案未知”与“无有效方案记录”分开；没有计划不能直接写“停药”，除非存在明确用户停用事实。所有时期默认可访问；大历史用惰性列表/分页加载，不能靠90天截断隐藏事实。未来预约/里程碑可标“未来”，不作为方案已经发生的依据；未来条目位置待审核。

## 六、回归与审核问题

### 实施后测试计划（本轮未新增测试代码）

### 已确定规则不重复提问

各时段剂量分配改变要切阶段、多药同日一次显示切点、具体提醒/锚点/时区不切、边界只显示日期、不改历史，是明确要求，不能作为“可否照旧”的选择。待决定的是实现边界与剩余产品取舍：

1. **停用后恢复同标准**：A新时期（建议），保留间隔并注明标准相同；B同一治疗标准主题下的多个不连续片段，间隔独立显示，不能用一个连续跨度掩盖停用。若没有明确停用事实，写无有效方案记录，不猜停药。
2. **卡片依从性事实计数**：A默认不显示（建议，最简且不和History重复）；B用户开关后显示迟服/确认漏服/未确认并注明仅已登记记录；C始终显示。具体是否显示迟服也由用户决定。
3. **两个视图**：A合并为一个时期列表（建议）；B保留两个入口但共享时期数据，必须说明它们为何不同，不恢复逐条服药列表。
4. **日期/时段边界**：是否采用本文“固定分组时区+变更日组+当日最终方案摘要+精确采样上下文”的方案？推荐不采用整日倒推新方案。纯改提醒穿越另一个剂量时段时，建议要求确认是否交换剂量分配，不能因钟点排序就暗切阶段。
5. **现有字段模糊处**：每周只换星期几而天数不变，建议不切；含服档位是模型设置还是治疗标准，建议不因仅PK输入改变切；单位变化缺换算依据先保持不同。完整制剂身份不足不猜补。以上细则待用户选择，不因影响PK而自动等同临床变化。
6. **Visit Pack**：先保留template1“方案版本开始/结束”的字面事实，还是另实施template2治疗标准变化计数？推荐template2与新时期政策一起单独验收，绝不改旧生成记录；不是本次自动授权。
7. **未来条目与修复批次**：建议允许未来预约/计划里程碑，中性标记且不算既已发生；未来独立区而不捏造未来方案。P0里程碑修复可先做一批，或与时期修订一起实施，由用户定。本轮无论哪种都停在审核。
