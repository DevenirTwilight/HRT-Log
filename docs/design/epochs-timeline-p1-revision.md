## 一、里程碑“开始激素治疗”保存后没反应：根因

### 复现（合成数据，Robolectric，本地探针测试，未提交）

| 步骤 | 结果 |
|---|---|
| 时间线 → 添加里程碑 → 类型选“开始激素治疗” → 保存 | 保存回调触发，`kind=STARTED`，按钮可用（`enabled = kind!="CUSTOM" \|\| title非空`，STARTED 无需标题） |
| ViewModel `saveMilestone` → `repo.saveMilestone` → `dao.milestone(@Upsert)` | 数据库中有该行，`state.error` 为空，无异常 |
| `LongitudinalProjection.build` | 产生 1 条 MILESTONE 事件 |
| 时间线页面：日期为 10 天前 | 显示 |
| 时间线页面：日期为 400 天前 | **不显示** |
| 切到“治疗阶段”视图 | 任何里程碑都**不显示** |

### 结论

1. **根因**：保存成功，但被时间线的显示筛选挡掉了。时间线默认只显示**最近 90 天**（`LongitudinalScreen` 中 `days` 默认 90）。“开始激素治疗”通常是几个月或几年前，日期一早于 90 天就被过滤；未来日期也会被过滤（除非打开“显示计划”）。另外“治疗阶段”视图只列阶段卡、从不列里程碑，而“添加里程碑”按钮在两个视图都显示。
2. **为什么像“没反应”**：对话框照常关闭，没有任何保存提示，列表又没有新条目，看起来就像点了没用。不是崩溃，也不是数据丢失。
3. **层级**：UI层（时间线的显示筛选与反馈），数据层正确。表上没有唯一性约束；触发器只检查日期长度、类型取值、CUSTOM 需要标题，STARTED 不受影响；协程异常会进 snackbar，本例没有异常。
4. **最小修复**（审核后实施）：保存或编辑里程碑后，如果它落在当前筛选之外，自动把范围切到“全部时间”、清除类型/阶段筛选、切回能显示它的视图，并滚动到它，同时给一条“已保存”提示。在第二部分的新时间线里，所有阶段和里程碑都会列出，这个问题从结构上消失；上面的最小修复可以先单独发一版。
5. **回归测试**：日期在 400 天前的 STARTED 保存后可见；从“阶段”视图添加后可见；编辑日期、改类型、删除；未来日期的处理（见“待决定”第 10 条）；ViewModel 重建（模拟进程重建后从数据库重新读取）仍可见；STARTED 日期只来自用户输入，不由最早服药记录推断（已有行为，保留断言）。

## 二、治疗阶段：新的判定规则

### 现状为什么切得太碎

- `RegimenDefinition.signature()` 把这些都算进去了：提醒时刻（`times` 的具体钟点）、周期相位（`phase`，由锚点计算）、时区（`zone`）。改一次提醒时间，`RegimenHistory.changed` 就会新建一个 `regimen_version`，`TreatmentEpochs.build` 又以每个版本的开始时刻为边界，于是多出一个阶段，边界精确到保存的那一分钟。
- 多药在同一天不同分钟修改，会切出几分钟长的阶段。

### 新规则

新增一个**只在投影时计算、不入库**的“治疗标准签名” `therapySignature`（v2）。只包含：

| 计入 | 说明 |
|---|---|
| 成分、途径、单位、酯型 | 现有字段 |
| 制剂 | 凝胶产品编号、贴片释放速率；舌下含服时长档位是否计入，待决定第 6 条 |
| 频率 | `kind`、`interval`；每周方案只计每周天数（具体星期几是否计入，待决定第 5 条） |
| 剂量 | 每次的量，以及**按时段先后排列的剂量序列**（例如 [1 mg, 2 mg]），**不含具体钟点**。所以 08:00→09:00 不变；早晚剂量互换会变；每天总量变化也会变 |

不计入：提醒钟点、周期锚点和相位、时区、名称、包装、库存、通知、提醒阈值。漏服、迟服、跳过、未确认本来就不是方案数据，不会切阶段。

**投影步骤**（取代 `TreatmentEpochs.build` 的输入预处理）：

1. 对每种药，按时间顺序把首尾相接（`until == 下一个.from`）且 v2 签名相同的 `regimen_version` 合并成一段“治疗段”，保留全部原始版本 ID 列表。
2. 把每段的开始和结束**对齐到当天日期**（按该版本保存的时区取本地日期），阶段区间为 `[开始日期, 结束日期)`。同一天的多处修改（无论几种药、几点改的）只产生一个切点；这一天属于新阶段。
3. 按这些日期边界组合出阶段；组合规则（多药成员集合不变即合并）沿用现状。
4. 界面只显示日期。

**停药后恢复相同标准**：见待决定第 1 条。推荐做法：中间有间隔就是新阶段，间隔期本身显示为“停用期”，阶段卡上注明“与某阶段相同标准”。

### 代码改动点

| 位置 | 改动 |
|---|---|
| `RegimenDefinition.signature()` | **不改**。它仍是 `regimen_version.clinical_signature` 和 `regimen_rule_link` 一致性校验（`validateLinks`）的依据；已有行受不可修改触发器保护 |
| `RegimenDefinition` | 新增 `therapySignature()`（v2），只供投影使用 |
| `RegimenHistory.changed` | 不改：仍然每次保存精确记录当时的完整指令（含钟点），作为事实 |
| `TreatmentEpochs` | 新增按“治疗段 + 日期边界”的构建函数；`TreatmentEpoch` 增加 `fromDate`/`untilDate` 和成员版本 ID 列表 |
| 阶段 key | 改为 `stage:v2:<开始日期>:<各治疗段首个版本ID，排序>`。之后同标准的新版本只会延长治疗段，不改变 key |
| `LongitudinalProjection` / `LongitudinalScreen` | 改成按阶段分组（见第三部分） |
| `LabContext.build` | 新化验的 `epoch` 字段使用 v2 阶段（日期与 key）；`regimens` 仍保存采样时刻**精确生效**的版本与完整定义 |
| Visit Pack 事实摘要 | “开始/结束的方案版本数”改为“阶段变化次数”，模板版本升到 2；已生成的资料包记录不变 |

### 数据兼容（不迁移）

- **不删除、不改写**任何服药记录和 `regimen_version` 行；schema 不变（仍为 6），不需要迁移和回滚方案。过去被切碎的阶段，打开时按新规则重新投影合并显示。
- **旧备份**：恢复流程不变（`seed` 和 `validateLinks` 仍用 v1 签名），恢复后同样重新投影。
- **已冻结的化验上下文**：里面保存的是旧格式 key `epoch:<毫秒>:<版本ID…>`、区间时刻、版本 ID 和完整定义。`LabContext.validate` 只做自身一致性校验，不依赖当前投影，所以旧记录继续有效、不重写。显示时：
  - 保留“当时记录的阶段区间”原值；
  - 另外用其中的版本 ID 找到它们按新规则所属的阶段，显示“按现行规则属于：2026-06-10 – 2026-08-31 阶段”。版本 ID 都还在库里，一定能解析；如果某个 ID 属于多个新阶段（不应发生），显示“无法唯一对应”，不猜测。
- **Visit Pack**：生成记录只存区间、勾选项、校验码和事实计数，不存阶段 key，不受影响。

## 三、时间线：按时期展示

### 规则

- 时间线就是阶段列表，**当前阶段在最上面**，过去的阶段依次往下。正常服药不单独出现，完整记录留在“历史”。
- 每个阶段一张卡（现有卡片样式，不画线段或甘特图）：日期区间；每种药一行“名称 途径 · 频率 · 每次剂量”（各时段剂量不同时写成“早 1 mg / 晚 2 mg”）。
- 卡片下列出本阶段的化验、阶段回顾、里程碑、预约：每条只显示日期、类型、标题，点进去看详情。卡片上不展开数值或全文。
- 每日状态、症状、漏服、迟服、跳过、未确认都不逐条列出。
- 第一个有记录的方案之前的时期，或中间停用的时期，显示为“无方案记录 / 停用期”卡，用来放落在其中的里程碑、化验等（例如“开始激素治疗”日期早于第一条方案时）。
- 精简模式：药物名称照常隐藏，与现有规则一致；四语文案齐全。

## 四、测试计划

全部使用合成数据。

| 范围 | 用例 |
|---|---|
| v2 签名 | 改提醒时刻不切阶段；改周期锚点/计时起点不切；改时区不切；改名称/包装/库存/通知不切 |
| 依从性 | 漏服、迟服、跳过、未确认不切阶段，也不逐条出现在时间线 |
| 切阶段 | 改每次剂量；改各时段剂量分配（总量不变）；改每天次数；改每 N 天；改每周天数；口服改凝胶；换凝胶产品；换贴片规格；换酯型；换药或新增、停用一种药 |
| 日期边界 | 多药同日不同时刻修改只切一次；当天全部属于新阶段；跨时区保存按版本时区取日期；夏令时日期 |
| 旧数据 | 预先切碎的版本序列（只改钟点）合并成一个阶段显示；`regimen_version` 行数和内容不变；阶段 key 在追加同标准版本后保持不变 |
| 兼容 | schema 1–6 旧备份恢复后投影正确；`validateLinks` 不变照常通过；冻结化验上下文中的旧 key 和旧版本 ID 都能解析到新阶段；Visit Pack 旧记录不受影响 |
| 时间线 | 当前阶段在最上；化验、回顾、里程碑、预约归入正确阶段；无方案期和停用期卡；精简模式；四语 TranslationsTest |
| 里程碑 | 新建（今天、400 天前、早于第一条方案）、编辑、删除；保存后自动显示并定位；ViewModel 重建后仍可见；STARTED 日期不由服药记录推断 |

## 五、与规则冲突或待你决定的地方

1. **停药后恢复同一标准**：A 新阶段（推荐，中间显示停用期，并注明“与某阶段相同标准”）；B 延续旧阶段（中间仍显示停用期）。
2. **日期对齐**：修改当天整天属于新阶段，所以当天早些时候、修改之前的服药在显示上归入新阶段。精确版本仍保留在化验上下文和详情里。是否接受？
3. **剂量分配**：每天总量不变、只是早晚剂量互换，按你的表格算变化（切阶段）。确认？
4. **单位改变但实际量相同**（如 mg 改 µg）：按单位不同算变化，还是换算后比较？推荐算变化（不做换算猜测）。
5. **每周方案**：只改“星期几”、天数不变（周一改周二）算不算频率改变？推荐不算，与提醒时刻同类。
6. **舌下含服时长档位**：算制剂或给药方式改变（切阶段）还是给药细节（不切）？推荐切阶段，因为它是现有浓度模型的输入。
7. **阶段卡上的漏服计数**：见第三部分建议。
8. **两个视图合并**：见第三部分建议。
9. **Visit Pack 摘要的“方案版本”计数**改为“阶段变化次数”，并把模板版本升到 2，是否同意。
10. **里程碑日期在未来**：现在的日期选择器允许选未来日期。建议允许（如计划中的手术），新时间线放在当前阶段卡顶部，标注“未来”；或者禁止未来日期。
11. **里程碑最小修复是否先单独发一版**（build 12），还是和阶段、时间线的修订一起做。
