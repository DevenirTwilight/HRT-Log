# 设计：时间线时期编辑（build 23，用户 2026-10-08 已定）

需求见 REQUIREMENTS §37。本文是实现方案。

## 数据（schema 8）

沿用只追加的 `history_period_revision`，新增两列：
- `kind TEXT NOT NULL DEFAULT 'CONFIRMED'`：`CONFIRMED`（已确认的识别时期，原有行）、`PERIOD`（用户新建或修改的时期，边界固定）、`FILL`（为改停用期补上的方案段，可与相邻同标准部分接续）、`DELETED`（已删除的范围）、`STOP`（用户设定的停用期）。
- `group_key TEXT`：一次操作写入的多行共用，撤销时整组撤销；`evidence_json.replaces` 记下被这次操作撤销的旧用户行，撤销本组时恢复它们。
- `origin`：`CONFIRMED` 行仍为 `OBSERVED_USER_CONFIRMED`，其余为 `USER_EDIT`。`DELETED`/`STOP` 的 `standard_json` 为 `{}`。
- 状态沿用 `CONFIRMED`（生效）/`REVOKED`（撤销）。触发器仍禁止修改和删除。
- 迁移 7→8：两次 `ALTER TABLE ADD COLUMN`。旧备份（schema 1–7）恢复时新列取默认值。

同一药物：生效的用户行（PERIOD/FILL/DELETED/STOP）互不重叠；CONFIRMED 行互不重叠（原规则）。用户行可以覆盖 CONFIRMED。

## 投影（只读显示，不写库）

优先级：用户行 > 已确认 > 应用保存 > 自动识别。
1. 应用保存的版本被同药用户行裁剪（不改版本本身）；裁剪出的后续片段用新的负 ID，`sourceId` 指回原版本。
2. 已确认时期被保存片段和用户行裁剪；自动识别被以上全部裁剪。
3. `PERIOD` 的边界固定，不与相邻部分自动合并；`FILL` 可接续。
4. `DELETED`、`STOP` 范围内没有方案，记录显示“方案未知”；`STOP` 作为停用期显示。
5. 14 天规则：持续 < 14 天的保存版本，若前一部分与后一部分标准相同，按前一部分的标准并入，并在卡片上注明原样。

## 操作

| 操作 | 写入 |
|---|---|
| 新建 | 1 行 PERIOD |
| 编辑（任何来源） | 撤销该范围内旧用户行，写 1 行 PERIOD（范围、标准为用户所填） |
| 拆开 | 撤销范围内旧用户行，写 2 行 PERIOD |
| 与下一段合并 | 撤销两段内旧用户行，写 1 行 PERIOD，标准由用户选前段/后段/自填 |
| 删除 | 撤销范围内旧用户行，写 1 行 DELETED |
| 改停用期 | 写 STOP，原停用期中不再停用的部分写 FILL（前段用前一方案标准，后段用后一方案标准） |
| 恢复 / 撤销我的修改 | 整组撤销，并恢复被替换的旧用户行 |

重叠检查（同药）：新范围不得与本次操作对象以外的同药方案段相交，否则提示先拆开或缩短旁边那段。

## 不变

原始记录、冻结快照、库存、方案版本与 V1 签名、已冻结的化验上下文、已生成的复诊资料包。编辑过去时期不影响提醒。
