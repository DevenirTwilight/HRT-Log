# 设计：时间线手动新建与修改时期（待用户审核，未实现）

日期：2026-10-08。用户提议“时间线支持自己新建修改，用户可以增删改东西，系统生成的也让改”。本文只是设计，审核前不写代码。

## 现状

- 自动识别的过去时期：可确认、改起止和频率剂量、在某天拆开、与下一段合并、撤销（`history_period_revision`，只追加）。
- 应用内保存的方案版本（`regimen_version`）：冻结，化验上下文、复诊资料包、V1 签名引用，不能改写。
- 停用期：由保存版本的结束时间推出，不能编辑。

## 目标

1. 新建过去时期：药物、起止日期、每几天一次、每个用药日的剂量。
2. 系统生成的都能改：识别时期（已有）、应用内保存方案（显示覆盖）、停用期起止。
3. 删除：只追加“已删除”修订，可恢复；服药记录永不删除；被删的那段记录显示“方案未知”。
4. 任意相邻两段可合并（不要求标准相同，合并后由用户指定标准），任意一段可在某天拆开。
5. 优先级：用户手动建或改 > 用户确认 > 应用保存方案 > 自动识别。

## 数据模型（schema 8）

- 扩展 `history_period_revision`：新增 `kind`（`OBSERVED_CONFIRMED` 原有、`USER_CREATED`、`OVERRIDE_SAVED`、`DELETED`、`STOP_OVERRIDE`）和可选 `target_regimen_id`（覆盖哪个保存版本）。只追加，修订号连续，触发器禁止修改和删除。
- 覆盖保存方案：不改 `regimen_version`，只在显示投影时用覆盖行替代该版本的区间和标准；撤销覆盖即恢复原样。
- 迁移 7→8：新列有默认值；旧行 `kind=OBSERVED_CONFIRMED`。旧备份（schema 1–7）恢复时新列取默认值，校验放宽到旧格式。

## 规则

- 同一药物的用户时期不得重叠；保存时提示先拆开或缩短相邻那段。
- 改过去时期不影响提醒；提醒只按药物当前设置的方案。
- 已冻结的化验上下文、已生成的资料包不变；新建或重建的使用新的显示投影，并注明“用户修改”。
- 精简模式可编辑，但不显示药名和剂量。
